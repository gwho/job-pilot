- **Company Research — Synthesis Recovery (Issue #38)**: `synthesizeDossier()` in `agent/research.ts` called `JSON.parse()` directly on Nemotron's raw output with no `finish_reason` check, no try/catch, and no runtime shape validation. Real runs returned both truncated JSON and prose, throwing an uncaught `SyntaxError` through `researchCompany()` to a generic 500 in `/api/agent/research` — a user could complete the expensive browser-research step and still get nothing. Diagnosed via `/diagnosing-bugs`: a red regression suite at `__tests__/agent/research-synthesis.test.ts` reproduced the exact production error strings (byte-for-byte match on the prose case) by driving `researchCompany()` through mocked OpenAI/InsForge/Hyperbrowser boundaries with browser research disabled (job fixture has no company/URL, so `deriveHomepageUrl()` short-circuits). Branch `fix/company-research-synthesis-recovery`, stacked on `fix/find-jobs-pipeline-reliability`.
- **AI Matching — Score/Skill Regression Recovery**: `scoreJobs()` in `agent/job-matcher.ts` had no `finish_reason` check, no Zod validation, no retry, and purely array-index alignment; on any failure (request error, malformed JSON, misaligned entry) it fabricated `matchScore: 0` via `FALLBACK_SCORE` — indistinguishable from a real 0% match once persisted by `app/api/agent/find/route.ts`, violating CONTEXT.md's "Unscored job" definition (explicitly "not a zero-score job"). There was also no rescore path: `source_url` dedup meant a job that got the fallback once stayed that way forever. Investigation found the DB column, `types/index.ts`, and every UI consumer (`JobInfo.tsx`, `MatchScore.tsx`, `JobsTable.tsx`, `FindJobsClient.tsx`, `app/dashboard/page.tsx`) already fully supported `match_score: null` as "unscored" — the bug was narrowly confined to the matcher fabricating `0` instead of using it. Fixed with a two-level contract: envelope validity (`finish_reason`, empty/non-JSON content, and a `{ scores: unknown[] }` shape check via `ScoringEnvelopeSchema`) gets exactly one whole-batch retry (2000 → 2600 tokens) on failure; per-entry validity (`JobScoreEntrySchema`, keyed by a 1-based `jobNumber` the model echoes back rather than trusting array position) is checked independently afterward, so one malformed, missing, or duplicated entry only leaves its own job unscored — duplicates are never resolved by first-wins. Terminal failure at either level is `matchScore: null` with `UNSCORED_MATCH_REASON`, never a fabricated number; unlike company research, job matching has no deterministic non-AI fallback score to fall back on. `app/api/agent/find/route.ts` now also folds up to 10 rediscovered existing rows (oldest `found_at` first) carrying the exact legacy fallback signature (`match_score === 0 && match_reason === UNSCORED_MATCH_REASON && ` empty skill arrays) or a plain `null` score into the same scoring batch as new jobs, updating those rows in place (never overwriting a valid score, never inserting a duplicate, never re-firing `job_found` for a rescored row) — a failed rescore attempt still normalizes the legacy `0` to `null` rather than leaving the old sentinel in place. `context/library-docs.md` documents the corrected token policy (was incorrectly documented as `300`) and the envelope/entry validation split. 25 new tests (`__tests__/agent/job-matcher.test.ts`, `__tests__/find-jobs/matching-reliability.test.ts`), full suite green.
