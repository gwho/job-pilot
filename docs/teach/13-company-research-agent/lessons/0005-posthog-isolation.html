Lesson 5 of 6

PostHog isolation

Side effects that must never change the user's outcome.

⏱ ~15 min reading + 15 min exercise 📘 project-review findings §analytics isolation 🗂 app/api/agent/research/route.ts · __tests__/api/agent/research/research.test.ts

Why this lesson matters: PostHog is analytics — it records that something happened. It is not the thing that happened. When analytics fails, the user's experience should be unchanged. But if the PostHog call sits inside the main try/catch and throws, it produces a 500 response — the user sees a failure even though the dossier was generated successfully. This lesson is about a class of bug that appears often: side effects that accidentally become load-bearing.

The concept: containment boundaries

Every API route has one primary obligation — complete its core operation and return the right response. Everything else is a side effect: logging, analytics, notifications, cache invalidation. A containment boundary is a try/catch that wraps a side effect so its failure cannot alter the primary outcome.

Without a containment boundary, this can happen:

User clicks "Research Company" ↓ Route: researchCompany() succeeds — dossier generated ✓ ↓ Route: captureServerEvent() throws — PostHog is down ↓ Outer catch block fires ↓ NextResponse.json({ success: false }, { status: 500 }) ↓ User sees: "Failed to research company" Actual state: dossier was saved to DB — it exists

With a containment boundary:

User clicks "Research Company" ↓ Route: researchCompany() succeeds — dossier generated ✓ ↓ Route: inner try: captureServerEvent() throws — PostHog is down ↓ Inner catch fires: console.error (logged, not rethrown) ↓ NextResponse.json({ success: true, data: { companyResearch: dossier } }) ↓ User sees: dossier rendered correctly

Here is the full route — every line:

export async function POST(req: NextRequest): Promise<NextResponse> {
  try {                                                     // ← outer try
    const insforge = await createInsforgeServer();
    const { data: authData, error: authError } =
      await insforge.auth.getCurrentUser();
    if (authError || !authData.user) {
      return NextResponse.json(
        { success: false, error: "Unauthorized" }, { status: 401 }
      );
    }

    const body = await req.json() as { jobId?: unknown };
    if (!body.jobId || typeof body.jobId !== "string") {
      return NextResponse.json(
        { success: false, error: "jobId is required" }, { status: 400 }
      );
    }

    const { jobId } = body;
    const userId = authData.user.id;

    const { dossier, company } = await researchCompany(jobId, userId);

    try {                                                   // ← inner try
      await captureServerEvent({
        distinctId: userId,
        event: "company_researched",
        properties: { userId, jobId, company: company ?? "" },
      });
    } catch {                                              // ← inner catch
      console.error(
        "[api/agent/research] PostHog capture failed — analytics only, research succeeded"
      );
    }

    return NextResponse.json(
      { success: true, data: { companyResearch: dossier } }
    );
  } catch (error) {                                        // ← outer catch
    console.error("[api/agent/research]", error);
    return NextResponse.json(
      { success: false, error: "Failed to research company" },
      { status: 500 },
    );
  }
}

The key structural detail: The inner try/catch ends before the return NextResponse.json({ success: true, ... }). The return is outside the inner try, still inside the outer try. This means: PostHog either succeeds (event captured) or fails (error swallowed) — but either way, execution always reaches the success return. The outer catch is never involved in the PostHog path.

Why company comes from researchCompany(), not the request body

The PostHog event includes company: company ?? "". Notice company comes from the destructured return value of researchCompany() — not from the request body.

Before the project review, this property was missing entirely. The fix could have been: read company from the client (body.company). But that would let the client send any string it wanted — a security and data integrity issue. Instead, researchCompany() was extended to return { dossier, company }, deriving the company name from the server-side job row. The PostHog event always contains the real company name from the database.

What the existing regression test does

This bug was caught by a project review, fixed, and then covered by a regression test. Open __tests__/api/agent/research.test.ts. The test at line 77 is the regression test for this exact isolation:

it("returns success:true with dossier even when captureServerEvent throws", async () => {
  vi.mocked(captureServerEvent).mockRejectedValue(
    new Error("PostHog unavailable")
  );

  const res = await POST(makeRequest({ jobId: "job-1" }));
  const body = await res.json() as { ... };

  expect(res.status).toBe(200);
  expect(body.success).toBe(true);
  expect(body.data?.companyResearch).toEqual(MOCK_DOSSIER);
});

Read this alongside the route code. For each line of the test, identify:

  • mockRejectedValue — makes PostHog throw when called. This simulates PostHog being down.
  • expect(res.status).toBe(200) — verifies the route's HTTP status is 200, not 500. This is the isolation guarantee.
  • expect(body.success).toBe(true) — verifies the response body says success, not error.
  • expect(body.data?.companyResearch).toEqual(MOCK_DOSSIER) — verifies the actual dossier data is in the response.

The test does not assert anything about the console.error call. It only cares about the user-facing outcome. This is correct: the test verifies a user-facing contract, not an internal implementation detail.

Predict what happens if…

Question: Suppose you move the return NextResponse.json({ success: true, ... }) inside the inner try block — after the PostHog call, before the inner catch. Like this:

try {
  await captureServerEvent({ ... });
  return NextResponse.json({ success: true, ... }); // ← moved here
} catch {
  console.error("PostHog failed");
}

What happens when PostHog throws? Does the user still get the dossier?

Reveal answer

When PostHog throws, the inner catch fires — the return inside the inner try is never reached. The inner catch logs the error but does not return. Execution falls through to the end of the outer try block — but there is now no return there either (it was moved inside the inner try).

A function that returns Promise<NextResponse> with no explicit return at the end returns undefined. Next.js would likely throw an error about an invalid response, or the route would return an empty response. The user would get an error.

This is a subtle placement bug. The success return must be outside and after the PostHog inner try/catch, not inside it. The inner try/catch must be a pure side-effect block with no return statement. That placement is what makes the isolation work.

This pattern has a name in software design: failure isolation or bulkhead pattern (from naval engineering — a bulkhead contains a flood in one compartment so the ship stays afloat). Search for "bulkhead pattern microservices" and read one short explanation. The same principle applies at every scale: a side effect that can fail should be isolated so its failure cannot sink the primary operation.

Ask your AI teacher: Ask it to explain the difference between a side effect and a primary effect in the context of an API route. Then ask: "What other side effects in a typical web API should have containment boundaries?" The list is longer than you might think: email notifications, webhooks, audit logs, cache invalidation, third-party integrations.
