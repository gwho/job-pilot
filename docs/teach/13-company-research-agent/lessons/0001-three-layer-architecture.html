Lesson 1 of 6

Why three tools for one job

Hyperbrowser owns the session. Stagehand owns the browser. Nemotron owns the reasoning.

⏱ ~20 min reading + 15 min exercise 📘 Tutorial 24, Parts 1–3 🗂 explanation.md §1–3

Why this lesson matters: Feature 13 uses three separate tools where one tool could theoretically do everything. Understanding why they are split lets you predict what breaks when any one of them fails — and that is the single most important skill for debugging agent code.

The concept: one responsibility per layer

The company research agent needs to browse the web. That sounds like one job. It is actually three very different jobs:

Tool Job File
Hyperbrowser Create and manage a remote Chrome browser session in the cloud lib/hyperbrowser.ts
Stagehand Connect to any browser via CDP and extract structured data using AI lib/stagehand.ts
Nemotron Reason: power Stagehand's extraction, then synthesise the final dossier agent/research.ts

Hyperbrowser and Stagehand are connected by a single value: session.wsEndpoint. That WebSocket URL is what Chrome's DevTools Protocol (CDP) listens on — it is how any external program talks to a running browser.

In hyperbrowser.ts, the session creation returns a session object:

const session = await client.sessions.create({
  useStealth: true,
  adblock: true,
  acceptCookies: true,
  timeoutMinutes: 2,
});
return { client, session };

In stagehand.ts, that session object's wsEndpoint arrives as the parameter cdpUrl:

export async function createStagehand(cdpUrl: string): Promise {
  const stagehand = new Stagehand({
    env: "LOCAL",
    localBrowserLaunchOptions: { cdpUrl },
    model: {
      modelName: "openai/nvidia/nemotron-3-ultra-550b-a55b:free",
      apiKey: process.env.OPENROUTER_API_KEY!,
      baseURL: "https://openrouter.ai/api/v1",
    },
    disablePino: true,
  });
  await stagehand.init();
  return stagehand;
}

The misleading name: env: "LOCAL" does not mean the browser runs on your machine. It means "I am supplying the browser via a CDP URL — do not launch one yourself." The browser is running on Hyperbrowser's cloud infrastructure. "LOCAL" tells Stagehand to skip its own browser launch and connect to the URL you provide instead.

How Nemotron appears twice

Nemotron does two completely separate jobs in this feature. The same model is used, but through different clients:

┌─────────────────── agent/research.ts ──────────────────────┐ │ │ │ conductBrowserResearch() │ │ └─ stagehand.extract(instruction, ZodSchema) │ │ └─ Stagehand → Nemotron via OpenRouter │ │ "What did this page say about tech stack?" │ │ │ │ synthesizeDossier() │ │ └─ openai.chat.completions.create(...) │ │ └─ Direct OpenAI-compatible client → Nemotron │ │ "Now combine everything into one dossier" │ │ │ └─────────────────────────────────────────────────────────────┘

The difference is in the client. Stagehand uses its own internal OpenAI provider (which is why the model name needs the "openai/" prefix). synthesizeDossier() uses the OpenAI SDK directly with baseURL: "https://openrouter.ai/api/v1", so the model name goes straight to OpenRouter without any prefix.

Trace the flow

Task: Open agent/research.ts and find the section that starts with let stagehand: Stagehand | null = null (around line 326). Read to the finally block. Answer these without looking back:

  1. Which line starts the Hyperbrowser session?
  2. Which line creates Stagehand?
  3. What single value is passed from one to the other?
  4. Which of the three variables (stagehand, session, client) is closed first in finally?

The expected answer for question 4: stagehand closes first. The CDP connection between Stagehand and the browser must be gracefully shut down before the browser itself stops. If Hyperbrowser stops first, Stagehand throws an error trying to close a connection to a dead browser.

Predict what happens if…

Question: The Hyperbrowser session is created with timeoutMinutes: 2. What happens if the research run takes 3 minutes — for example, if a company sub-page is extremely slow to load?

Think through: does Hyperbrowser kill the session? Does Stagehand notice? Where in the code does the failure appear? Does the user see an error or a partial result?

Reveal answer

After 2 minutes, Hyperbrowser forcibly terminates the session. The CDP WebSocket connection drops. Stagehand's next call (likely a page.goto() or stagehand.extract()) throws an error — "connection closed" or similar. That error is caught by the try/catch inside conductBrowserResearch() (which already wraps each sub-page in its own try/catch). The error is logged to agent_logs. Execution continues to synthesizeDossier(), which runs with whatever partial content was collected before the timeout. The user receives a dossier — possibly with fewer sources or less specific content, but not an error state.

Task: Read the finally block and the three null declarations above it. Answer the following without running any code:

  1. What happens to the finally block if createHyperbrowserSession() throws — before stagehand or session are ever assigned?
  2. What happens to the finally block if createStagehand() throws — after client and session are assigned but before stagehand is assigned?
  3. What happens to the finally block if conductBrowserResearch() throws — after all three are assigned?

Expected behavior: The finally block runs in all three scenarios. The if (stagehand) and if (client && session) guards determine which cleanup actions actually execute, preventing errors from calling methods on variables that were never assigned.

Manual checks:

  • Scenario 1 (Hyperbrowser creation fails): both guards are false. Neither cleanup runs. No second error is thrown.
  • Scenario 2 (Stagehand creation fails): stagehand is null, so Stagehand cleanup skips. client and session are assigned, so client.sessions.stop(session.id) runs.
  • Scenario 3 (research throws after full init): both guards are true. Stagehand closes first, then the Hyperbrowser session stops.

Hint: The cleanup order (Stagehand first, then Hyperbrowser) matters because Stagehand holds an open CDP connection to the browser. If the browser stops first, Stagehand throws when trying to close a dead connection — which can mask the original error. Closing in dependency order avoids this.
