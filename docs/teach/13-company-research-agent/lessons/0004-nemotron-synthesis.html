Nemotron synthesis

JSON mode, token budgets, and why you parse the response by hand.

⏱ ~20 min reading + 15 min exercise 📘 Tutorial 24, Part 5 🗂 agent/research.ts lines 194–285

Why this lesson matters: Nemotron appears twice in Feature 13. The first time is inside Stagehand — it controls the browser and extracts structured page content. The second time is a direct API call in synthesizeDossier(). This is the reasoning call: it reads everything collected and produces the personalised dossier. These are two different use patterns, with different configuration, different constraints, and different failure modes. This lesson covers the direct call.

The concept: JSON mode vs. Zod validation

In Lesson 3, Stagehand validated Nemotron's output against a Zod schema. synthesizeDossier() does something different. It sets:

response_format: { type: "json_object" }

This is JSON mode — a parameter supported by OpenRouter-compatible models that tells the model to return syntactically valid JSON rather than prose. It does not guarantee that the JSON matches your expected shape. That distinction matters:

Stagehand extract(): Sends JSON Schema → Nemotron must match it exactly Stagehand validates output → ZodError if mismatch You receive a typed TypeScript object synthesizeDossier() direct call: No schema sent → Nemotron matches the shape in the system prompt json_object mode → output is valid JSON, shape not enforced You receive a string → you call JSON.parse() yourself You cast each field manually with ?? [] defaults

Why not send a Zod schema to synthesis too? Because the synthesis call has a much richer system prompt — it includes grounding rules, personalisation rules, and output format — and the JSON Schema generated from a Zod schema would compete with those instructions. For structured extraction from a page, schema validation is precise and reliable. For open-ended synthesis, the system prompt is the contract.

Here is the full synthesis call:

const response = await openai.chat.completions.create({
  model: "nvidia/nemotron-3-ultra-550b-a55b:free",
  response_format: { type: "json_object" },
  temperature: 0.4,
  max_tokens: 2000,
  messages: [
    { role: "system", content: systemPrompt },
    { role: "user", content: userPrompt },
  ],
});

And the response handling:

const rawContent = response.choices[0]?.message?.content;
if (!rawContent) {
  throw new Error(
    "Nemotron returned empty content — model may be unavailable or rate-limited"
  );
}
const raw = JSON.parse(rawContent) as Record<string, unknown>;

const allSources = [
  ...((raw.sources as string[] | undefined) ?? []),
  ...content.visitedUrls,
].filter(Boolean);

return {
  companyOverview: (raw.companyOverview as string) ?? "",
  techStack: (raw.techStack as string[]) ?? [],
  culture: (raw.culture as string[]) ?? [],
  whyThisRole: (raw.whyThisRole as string) ?? "",
  yourEdge: (raw.yourEdge as string[]) ?? [],
  gapsToAddress: (raw.gapsToAddress as string[]) ?? [],
  smartQuestions: (raw.smartQuestions as string[]) ?? [],
  interviewPrep: (raw.interviewPrep as string[]) ?? [],
  sources: [...new Set(allSources)],
  researchedAt: new Date().toISOString(),
};

Why temperature: 0.4 and max_tokens: 2000

Temperature controls how random the model's output is. At 0, the model always picks the highest-probability next token — fully deterministic, no creativity. At 1, it samples broadly. The synthesis call uses 0.4: low enough that factual claims stay grounded (the model does not diverge into confabulation), high enough that it can phrase things naturally and draw non-obvious connections between the candidate's profile and the company's context.

For comparison, Stagehand uses temperature 0 or very low by default for extraction — page facts should be copied faithfully, not reinterpreted. Synthesis is a reasoning task, so a small amount of sampling helps quality.

Token budget: The dossier has 9 string/array fields. The project review calculated:

companyOverview — ~100 tokens (one paragraph) techStack — ~50 tokens (6-8 items) culture — ~80 tokens (4-5 items) whyThisRole — ~80 tokens (one paragraph) yourEdge — ~80 tokens (4-5 items) gapsToAddress — ~80 tokens (3-4 items) smartQuestions — ~120 tokens (4-5 questions) interviewPrep — ~120 tokens (4-5 items) sources — ~60 tokens (3-5 URLs) JSON structure — ~30 tokens (keys, braces, quotes) ───────────── Total estimate: ~800 tokens max_tokens: 2000 → gives 2.5× headroom

Setting max_tokens too low truncates the JSON mid-object, producing unparseable output. Setting it too high wastes credits. 2000 is calibrated to cover even verbose dossiers with room to spare.

The model name difference

In lib/stagehand.ts, the model name is:

modelName: "openai/nvidia/nemotron-3-ultra-550b-a55b:free"

In synthesizeDossier(), it is:

model: "nvidia/nemotron-3-ultra-550b-a55b:free"

The difference is the openai/ prefix. Stagehand uses OpenRouter but routes through its internal OpenAI-compatible provider wrapper — that prefix tells Stagehand's client which provider adapter to use. The direct OpenAI client in synthesizeDossier() already points at baseURL: "https://openrouter.ai/api/v1", so OpenRouter handles routing — no prefix needed. Same model, two different call paths.

Why ?? [] and ?? "" on every field

JSON.parse(rawContent) returns Record<string, unknown> — all field types are erased. When you cast raw.techStack as string[], TypeScript accepts it at compile time, but if Nemotron returned null or omitted the field, the cast would produce null or undefined at runtime. The ?? [] defaults ensure every field in the returned dossier is always the correct type — never null, never undefined.

This is important because CompanyResearchDossier has no optional fields — every array is string[], not string[] | null. The ?? operators are the bridge between the untyped world of JSON parsing and the typed world of the dossier.

The fallback path

When browser research fails entirely, content.homepageUrl is "" (the initial value set at line 322). Lines 208–211 check this:

const companyResearchText = content.homepageUrl
  ? `Homepage (${content.homepageUrl}): ${JSON.stringify(content.homepage)}
${content.subpages.map(...)}`
  : "No browser research available — synthesize from job posting and candidate profile only.";

When homepageUrl is empty, the ternary's falsy branch fires. The user prompt still goes to Nemotron — but with that fallback string where the company research would have been. Nemotron synthesises from the job title, job description, matched/missing skills, and the candidate's profile alone. The dossier is less rich, but structurally identical. The UI renders the same component either way.

content.visitedUrls: ["https://stripe.com", "https://stripe.com/blog"]

allSources before filter:

After .filter(Boolean): same — all four are truthy strings, nothing removed.

After new Set(): ["https://stripe.com", "https://stripe.com/about", "https://stripe.com/blog"] — the duplicate stripe.com is removed. Three unique URLs in the final dossier.

Why two sources lists? Nemotron may cite URLs it inferred from the page content that the agent did not actually visit — links it saw referenced in the text. content.visitedUrls contains only pages the agent actually navigated to. Merging them gives the most complete attribution.

Question: Suppose max_tokens is changed from 2000 to 200. Nemotron starts generating the dossier and runs out of tokens mid-way through the JSON — the response ends at "techStack": ["TypeScript", "Go", with the array incomplete.

Which line throws first? What type of error is it? What does the user see?

Reveal answer

rawContent is not null — Nemotron returned something. The null-check at line 263 passes. Line 266 calls JSON.parse(rawContent) on a truncated, invalid JSON string. JSON.parse() throws a SyntaxError: Unexpected end of JSON input (or similar).

This is not caught inside synthesizeDossier() — there is no try/catch around the parse call. The error propagates up to researchCompany() at line 352: const dossier = await synthesizeDossier(...). This is inside no try/catch either. The error propagates up to the API route's catch block, which returns { success: false, error: "Failed to research company" }. The user sees the error state in the UI — not the truncation details, just the generic error message.

This is different from browser research failures, which are always contained. Synthesis failure is uncontained — it propagates all the way to the route. The design decision here is deliberate: a dossier with truncated JSON cannot be partially used, so there is no partial-result path.

Ask your AI teacher: Ask it to explain what a language model's temperature parameter actually controls — in terms of the probability distribution over next tokens.
