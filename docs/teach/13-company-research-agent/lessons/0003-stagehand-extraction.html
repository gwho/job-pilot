Lesson 3 of 6

Stagehand extraction

Zod schemas are contracts between your code and an AI browser — not just types.

⏱ ~20 min reading + 15 min exercise 📘 Tutorial 24, Part 4 🗂 agent/research.ts lines 16–34, 132–188

Why this lesson matters: Stagehand does not return a string you parse yourself. You hand it a Zod schema and it returns a typed object. That schema is not just a TypeScript convenience — it is sent to Nemotron as the output specification. Every field you mark .optional(), every .describe() you write, and every field you make required all change what the model is asked to produce and what happens when the page does not have the data.

The concept: schema as AI contract

When you call stagehand.extract(instruction, schema), two things happen under the hood:

1. Stagehand reads the current browser page content 2. It sends to Nemotron (via OpenRouter): - The page content as context - Your instruction string (tells it what to look for) - Your Zod schema converted to a JSON Schema (tells it the output shape) 3. Nemotron returns JSON that matches the schema shape 4. Stagehand validates the JSON against your Zod schema 5. You receive a typed TypeScript object

This means:

  • The .describe("...") calls are model instructions, not code comments — they go into the prompt
  • Making a field .optional() signals to Nemotron that the field is nullable — it will not force-generate a value when the page lacks it
  • Making a field required tells Nemotron it must produce something — which can cause hallucination when the page genuinely lacks the content
  • If Nemotron's output doesn't match the schema, Stagehand throws

Here are the two schemas. Read each field carefully:

const HomepageSchema = z.object({
  oneLiner: z.string()
    .describe("What the company does in one sentence")
    .optional(),
  productSummary: z.string()
    .describe("What they build/sell and who it's for")
    .optional(),
  signals: z.array(z.string())
    .describe("Funding, notable customers, scale, mission, recent news")
    .optional(),
  pageLinks: z.array(z.object({
    url: z.string(),
    kind: z.enum(["about", "careers", "blog", "engineering",
                  "product", "team", "other"]),
  }))
    .describe("Internal links worth visiting")
    .optional(),
});

const SubpageSchema = z.object({
  keyPoints: z.array(z.string()).optional(),
  technologies: z.array(z.string())
    .describe("Specific languages, frameworks, tools, platforms")
    .optional(),
  valuesOrCulture: z.array(z.string())
    .describe("Stated values, working style, team norms")
    .optional(),
  notable: z.array(z.string())
    .describe("Customers, funding, scale, projects, awards")
    .optional(),
});

type HomepageData = z.infer<typeof HomepageSchema>;
type SubpageData = z.infer<typeof SubpageSchema>;

Notice: Every single field is .optional(). This is not laziness — it is correctness. Company websites vary wildly. A page might have a clear one-liner. Or it might be all images. Or it might be a 10,000-word wall of marketing prose. Making fields optional tells Nemotron: "return this if you can find it, return nothing if you cannot." The alternative — required fields — means Nemotron must produce something, and when the data isn't there, it invents it.

How .describe() becomes a prompt

Consider this field:

signals: z.array(z.string())
  .describe("Funding, notable customers, scale, mission, recent news")
  .optional(),

Stagehand converts this Zod schema to JSON Schema before sending it to Nemotron. The JSON Schema representation of this field looks like:

{
  "signals": {
    "type": "array",
    "items": { "type": "string" },
    "description": "Funding, notable customers, scale, mission, recent news"
  }
}

That "description" key is read by Nemotron as a hint about what to put in the field. Without it, Nemotron has only the field name "signals" to guide it. With it, it knows specifically to look for funding announcements, named customers, and mission statements. A missing .describe() produces lower-quality extraction — and you can't fix that at runtime.

How extraction is called

Here is the homepage extraction call (lines 152–155):

const homepageData = await stagehand.extract(
  "This is a company's homepage. Capture what the company actually does,
   who it's for, and any concrete signals (funding, customers, scale,
   mission, recent launches). Then find the internal links most worth
   visiting to research them as an employer.",
  HomepageSchema,
);

content.homepage = homepageData;

The first argument is the instruction — a natural language description of what to look for on the page. The second argument is the schema — the typed output shape. They work together: the instruction tells the model what to focus on, the schema tells it what shape to return it in.

And the sub-page extraction (lines 173–177):

const subData = await stagehand.extract(
  "Extract substance that helps a candidate understand this company
   before applying: what they do, their values and how they work,
   the specific technologies and tools they use, notable projects or
   customers, and how the team operates. Ignore nav, footers, cookie
   banners, and generic marketing copy.",
  SubpageSchema,
);

Different instruction, different schema, same pattern. The instruction can tell Nemotron what to ignore — "Ignore nav, footers, cookie banners" — not just what to extract. This is part of the contract too.

What happens after extraction fails

Look at lines 160–163:

if (!homepageData.oneLiner && !homepageData.productSummary) {
  return content;
}

If Nemotron extracted the homepage but could not find either a one-liner or product summary — the page was probably a login wall, a blank page, or pure image content — the function returns early. There is no error thrown. The sub-pages are simply never visited. Synthesis still runs later with the empty homepage data.

Sub-page failures are handled individually (lines 179–181):

} catch (subErr) {
  await logAgentError(userId, job.id,
    `[agent/research] Sub-page failed (${link.url}): ${String(subErr)}`);
}

Each sub-page has its own try/catch inside the loop. A failure on one sub-page does not stop the others. The error is logged to agent_logs, and the loop continues. This is deliberate: partial data is better than no data, and synthesis can always work with whatever was collected.

Question: Suppose you removed .optional() from oneLiner in HomepageSchema. The field is now required. You research a company whose homepage is a full-page video with no text — Nemotron reads the page and cannot find a one-liner.

Walk through exactly what happens at runtime: which line throws, what type of error is it, what catches it, where does the error end up, and does the user see it?

Reveal answer

Nemotron, facing a required field with no data on the page, has two choices: hallucinate something or return nothing. If it returns nothing (omits oneLiner), Zod validation fails at line 152 when Stagehand validates the response against HomepageSchema. The error is a ZodError with a message like "Required" at path ["oneLiner"].

This throws inside the outer try block (lines 145–185). It is caught at line 183. logAgentError() logs: "[agent/research] Homepage extraction failed: ZodError..." to agent_logs.

Execution reaches line 187: return content — with empty homepage data. Back in researchCompany(), synthesis still runs. The user sees a dossier generated from the job description and their profile only. They never see the error. The user experience is identical to a page that loaded but had thin content.

The second risk: Nemotron might not omit it — it might hallucinate a plausible one-liner for the company. The dossier would contain a fabricated company description presented as fact. This is why the whole schema is .optional(): empty is honest; invented is dangerous.
