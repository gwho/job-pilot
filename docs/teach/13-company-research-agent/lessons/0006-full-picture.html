The four UI states

Open CompanyResearch.tsx. The component manages three pieces of state:

const [research, setResearch] = useState<CompanyResearchDossier | null>(initialResearch);
const [loading, setLoading] = useState(false);
const [error, setError] = useState<string | null>(null);

These three booleans combine into four visible states:

State research loading error
Idle / empty null false null
Loading (first run) null true null
Error null false "..."
Success (dossier shown) { ... } false null

Notice there is no "Loading while dossier is shown" state. That is intentional — if the user clicks "Re-research" while a prior dossier is visible, loading becomes true but research still holds the old data. The dossier stays on screen while the new one is being generated. The button changes to "Researching…" but the content does not disappear. This is a better experience than blanking the screen.

The sources rendering pattern

Read lines 239–254 of CompanyResearch.tsx:

{research.sources.map((src, i) => {
  const isUrl = src.startsWith("http://") || src.startsWith("https://");
  return isUrl ? (
    <li key={i}>
      <a
        href={src}
        target="_blank"
        rel="noopener noreferrer"
        className="text-xs text-text-muted hover:text-text-secondary
                   underline-offset-2 hover:underline transition-colors
                   block truncate"
      >
        {src}
      </a>
    </li>
  ) : (
    <li key={i} className="text-xs text-text-muted truncate">{src}</li>
  );
})}

Two things to notice:

1. The URL check is explicit: src.startsWith("http://") || src.startsWith("https://"). Not src.includes("."). Not a regex. Not URL.canParse(). The check matches exactly what makes something safe to put in an href attribute — a full absolute URL with a known scheme. Nemotron might return something like "Stripe engineering blog" as a source citation. That string must render as plain text, not as a broken link.

2. Both security attributes together:

rel="noopener" — prevents the new tab from accessing window.opener (blocks a class of tab-napping attacks where an opened page can navigate its opener to a phishing URL) rel="noreferrer" — prevents the browser from sending a Referer header to the destination (privacy; the destination can't see which page linked to it) Together: rel="noopener noreferrer" ← always pair them

The rule is simple: every target="_blank" link must have both. A target="_blank" without them is a security vulnerability in modern web apps.

Reveal trace

Step 9: synthesizeDossier() throws. There is no try/catch inside synthesizeDossier() for this — the throw propagates.

Step 9 → researchCompany(): const dossier = await synthesizeDossier(...) at line 352 of agent/research.ts. No try/catch here either. The error propagates out of researchCompany().

Step 5 → route.ts: const { dossier, company } = await researchCompany(jobId, userId) at line 23. No try/catch around this line specifically — but it is inside the outer try. The error propagates to the outer catch at line 36.

Outer catch: console.error("[api/agent/research]", error) logs the rate-limit error server-side. Then returns NextResponse.json({ success: false, error: "Failed to research company" }, { status: 500 }).

Browser: fetch() resolves with status 500. In handleResearch(), the code checks body.success — it is false. The else branch fires: setError(body.error ?? "Something went wrong..."). setLoading(false).

User sees: The error banner appears at the top of the component. The button re-enables. The dossier panel (if there was a previous research) stays or the empty state shows. The user can retry.

Note that the finally block in researchCompany() (lines 341–348) still runs — Stagehand is closed and the Hyperbrowser session is stopped even though synthesis failed.

Predict what happens if…

Question: Suppose the DB write at step 10 fails (network blip). The dossier was successfully generated by Nemotron. Does the user see the dossier?

Look at the code in researchCompany() around the DB update. Is it inside a try/catch? What happens to the error?

Reveal answer

The DB update at lines 355–359 of agent/research.ts is not inside a try/catch:

await insforge.database
  .from("jobs")
  .update({ company_research: dossier })
  .eq("id", jobId)
  .eq("user_id", userId);

If this throws, the error propagates to the route's outer catch, which returns a 500. The user sees "Failed to research company." The dossier was generated but never reached the client and was not saved.

This is a design trade-off. The DB write is treated as a primary operation, not a side effect — if the dossier can't be persisted, the feature has partially failed. Returning the dossier without saving it would mean the user has it on screen but it disappears on page refresh. Whether that's better or worse than a 500 is a product decision, not a technical one. The current code treats persistence as non-optional.
