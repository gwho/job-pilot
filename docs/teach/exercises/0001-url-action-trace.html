Exercise 0001

Trace URL Changes

For each scenario below, predict the URL after each user action. Work from the code in FindJobsClient.tsx — do not run the app yet.

How to use this exercise: read the starting URL and the list of actions. Write down your predicted URL after each action on paper or in a text file. Then reveal the answer and compare. The goal is to notice the moment your prediction diverges from reality — that moment tells you exactly which concept needs more attention.

Scenario 1 — Basic filter chain

Starting URL:

/find-jobs

Actions:

  • 🖱️ User clicks "High Match" filter button
  • 🖱️ User clicks sort dropdown and selects "Newest"
  • 🖱️ User clicks page 2
Reveal answers (step by step)

After "High Match": /find-jobs?match=high&page=1
Why page=1? The handler is replaceViewState({ match: next, page: 1 }) — match changes always reset to page 1.

After "Newest": /find-jobs?match=high&page=1&sort=newest
Why is match still there? replaceViewState copies the current params first (new URLSearchParams(searchParams.toString())) before applying the update. Only sort changes.

After page 2: /find-jobs?match=high&page=2&sort=newest
Why replace, not push? Pagination is a refinement of the current view. onPageChange calls replaceViewState({ page: p }).

Scenario 2 — Text filter debounce

Starting URL:

/find-jobs?match=high

Actions:

  • ⌨️ User types "r" in the text filter input
  • ⌨️ User immediately types "e" (50ms after the previous keystroke)
  • ⌨️ User immediately types "a" (50ms after)
  • ⏱️ User stops typing. 300ms passes.

Hint: think about what the debounce timer does when the user types before it fires.

Reveal answers

After "r": URL is still /find-jobs?match=high. The debounce timer starts (300ms). filterTextDraft = "r".

After "e" (50ms later): URL still /find-jobs?match=high. The previous debounce timer was cancelled by the cleanup function. A new 300ms timer starts. filterTextDraft = "re".

After "a" (50ms later): URL still /find-jobs?match=high. Timer cancelled again. New timer starts. filterTextDraft = "rea".

After 300ms: URL becomes /find-jobs?match=high&page=1&q=rea. The timer fired and called replaceViewState({ q: "rea", page: 1 }). Page resets to 1. The match filter is preserved because replaceViewState only changes the keys you specify.

Scenario 3 — Back navigation restores state

Starting URL:

/find-jobs?match=high&q=react&page=2

Actions:

  • 🖱️ User clicks a job row (Feature 12 — uses router.push("/find-jobs/42"))
  • ⬅️ User presses the browser back button

After pressing back, what does the text filter input show?

Reveal answers

After clicking the job: URL is /find-jobs/42. A new history entry was added (push).

After pressing back: URL is /find-jobs?match=high&q=react&page=2. The browser restores the previous history entry.

What does the text input show? "react". When the URL changes, q becomes "react". Effect 1 fires: setFilterTextDraft("react"). The input immediately updates. Effect 2 fires but sees filterTextDraft === q → exits early. No loop.

Scenario 4 — Invalid URL params

Starting URL (user typed this manually):

/find-jobs?match=banana&page=-1&sort=NEWEST

What will the filter, page, and sort actually be when the component renders?

Reveal answer

match: "all". parseMatch("banana") — "banana" is not in ["all", "high", "low"] → fallback to "all".

page: 1. parsePage("-1") — parseInt gives -1, which fails n > 0 → fallback to 1.

sort: "score". parseSort("NEWEST") — "NEWEST" is not in ["score", "newest", "oldest"] (case-sensitive comparison) → fallback to "score".

The table renders with defaults. No crash. No error message. The URL still shows the invalid values — the parse helpers only coerce for use, they do not rewrite the URL.

Scenario 5 — Filter reduces page count

Starting URL:

/find-jobs?match=all&page=5

All Matches has 100 jobs (5 pages of 20). The user switches to "High Match", which has 15 jobs (1 page).

What is safePage? What slice of jobs does the user see?

Reveal answer

page from the URL is 5. totalPages is 1 (15 jobs / 20 per page, rounded up). safePage = Math.min(5, 1) = 1.

The slice is filtered.slice(0, 20) — all 15 High Match jobs, starting at index 0. The user sees page 1 of results, not an empty page.

The URL still says page=5 — the clamping is silent (it does not call replaceViewState). If the user then changes another filter, the next replaceViewState call will include page=1 explicitly and clean it up.
