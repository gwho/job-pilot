CSS tokens inside charts

How var(--color-accent) reaches inside SVG — and why it matters for design systems

⏱ ~20 min 📘 Tutorial 27, Parts 4 & 5 🎯 CompanyResearchChart, JobsFoundChart, MatchScoreChart

Why this lesson matters for your mission: Every dashboard you will ever build has charts. Charts are SVG. SVG uses its own color system. Understanding how design tokens reach inside SVG means you can build charts that automatically update when the design system changes — and explain to a client why their "brand color update" doesn't require manually editing 20 chart components.

The problem: charts don't use CSS classes

In HTML, you style elements with CSS classes: <div class="bg-accent">. The Tailwind class compiles to a CSS rule that sets background-color: var(--color-accent). The token system works through the cascade.

Charts are different. Recharts renders SVG, and SVG uses attributes for colors — not CSS classes:

<!-- HTML element — styled with a class -->
<div class="bg-accent"></div>

<!-- SVG element — styled with an attribute -->
<rect fill="#9B5CF6"></rect>

You can't write <Bar class="bg-accent">. Recharts doesn't accept class names as color props. It accepts SVG attribute strings: fill="...", stroke="...".

So how do you keep charts inside the design token system?

The answer: CSS custom properties resolve in SVG attribute values

Modern browsers resolve CSS custom properties (CSS variables) in SVG presentation attribute values. This is the key fact.

When a browser encounters:

<rect fill="var(--color-accent)"></rect>

It looks up --color-accent in the CSS cascade for that element and substitutes the resolved value at paint time. The visual result is identical to fill="#9B5CF6" — but the token is in control, not the hex value.

This is exactly what all three chart components in the dashboard use. Open components/dashboard/CompanyResearchChart.tsx:

<CartesianGrid
  strokeDasharray="3 3"
  stroke="var(--color-border)"
  vertical={false}
/>
<XAxis
  dataKey="day"
  tick={{ fill: "var(--color-chart-axis)", fontSize: 12 }}
  axisLine={false}
  tickLine={false}
/>
<Bar
  dataKey="count"
  fill="var(--color-info)"
  radius={[4, 4, 0, 0]}
/>

Every color is a CSS variable string. Not a single hex value. If --color-info changes in app/globals.css, the blue bars update automatically — no component file touched.

app/globals.css DOM (after render) ────────────────────── ────────────────────────────────── :root { --color-info: #61A8FF; <rect fill="var(--color-info)"> --color-accent: #9B5CF6; │ --color-border: #E5E7EB; ▼ browser resolves at paint time --color-chart-axis: #9ca3af; fills with #61A8FF }

A new token had to be added

Chart axis labels use a specific gray color: #9CA3AF. Before Feature 14, this color had no CSS variable in the project's @theme block. The only option would have been to hardcode the hex in all three chart components — three violations of the "no hardcoded colors" rule.

The solution: add one line to app/globals.css:

/* Charts */
--color-chart-axis: #9ca3af;

Now all three chart files can use var(--color-chart-axis). One source of truth. If the axis color needs to change for dark mode or accessibility, it changes in one place.

This is the recurring pattern in the design system: whenever you find yourself about to write the same raw value in two places, that value needs a name.

The gradient: SVG defs and paint servers

The JobsFoundChart has a more advanced color: an area fill that fades from semi-transparent accent at the top to fully transparent at the bottom. Solid colors can't do this. It requires a gradient.

Open components/dashboard/JobsFoundChart.tsx and look at the <defs> block:

<AreaChart data={data}>
  <defs>
    <linearGradient id="jobsGradient" x1="0" y1="0" x2="0" y2="1">
      <stop
        offset="5%"
        stopColor="var(--color-accent)"
        stopOpacity={0.2}
      />
      <stop
        offset="95%"
        stopColor="var(--color-accent)"
        stopOpacity={0}
      />
    </linearGradient>
  </defs>
  <Area
    fill="url(#jobsGradient)"
    stroke="var(--color-accent)"
    strokeWidth={3}
    dot={false}
  />
</AreaChart>

Breaking this down:

  • <defs> — an SVG section for reusable definitions. Elements inside don't render directly; they're referenced by others.
  • <linearGradient id="jobsGradient"> — defines a gradient named "jobsGradient". The x1/y1/x2/y2 vector runs top-to-bottom (y goes 0 → 1).
  • stopColor="var(--color-accent)" — the gradient uses the design token, not a hex value. Same CSS variable resolution as before.
  • fill="url(#jobsGradient)" — the area references the gradient by id. url(#id) is SVG's way of saying "use this definition as the paint source."
  • stroke="var(--color-accent)" — the line itself is a solid accent color. Gradient only applies to the fill area.

Important constraint: The gradient id="jobsGradient" must be unique within the SVG document. Currently the dashboard has one area chart, so there's no collision. If a second area chart were added with the same id, both would share the last gradient definition — a silent visual bug with no error message.

Try it in DevTools

Run npm run dev and navigate to /dashboard. Open DevTools (⌘+Option+I on Mac) and click on one of the blue bars in the Company Research chart.

In the Elements panel, find the selected <rect> element. Look at its fill attribute. You'll see fill="var(--color-info)" — the CSS variable string, not a resolved hex value. The browser holds the variable reference in the attribute; it resolves the actual color at paint time.

Now go to the Computed tab (still in DevTools). Search for fill. You'll see the computed fill value — the actual hex color the browser resolved. This is the color that gets painted on screen.

Bar charts use a solid fill color — no gradient needed. The area chart fades from opaque at the top to transparent at the bottom, which requires a <linearGradient> paint server.
