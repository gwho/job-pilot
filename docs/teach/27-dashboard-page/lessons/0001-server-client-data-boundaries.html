Lesson 1 of 4

When does code run?

Server Components, Client Components, and the dashboard split

⏱ ~20 min 📘 Tutorial 27, Parts 3 & 7 🎯 Feature 14 Dashboard

Why this lesson matters for your mission: The server/client split is the first thing to understand about any data-driven web app — it determines where data is fetched, who pays the cost, and what the user can and can't interact with. Once you can name this boundary, you can explain the architecture of almost any modern web dashboard to a client or colleague.

The question every React file answers

Every file in a Next.js App Router project is either a Server Component or a Client Component. The rule is simple: by default, every file is a Server Component. A file only becomes a Client Component when it has "use client" as its very first line.

In the JobPilot dashboard, six new components were built. Let's look at which ones have "use client" and which don't:

Component Type Why
ProfileBanner Server Renders HTML from a boolean — no browser APIs needed
StatsBar Server Renders cards from props — no state, no browser APIs
RecentActivity Server Renders a list from props — no state, no browser APIs
CompanyResearchChart Client Uses recharts — requires browser DOM to render SVG
JobsFoundChart Client Uses recharts — requires browser DOM to render SVG
MatchScoreChart Client Uses recharts — requires browser DOM to render SVG

The pattern is exact: three charts need "use client". Everything else doesn't.

What "Server Component" actually means

A Server Component runs only on the server. Its code is never sent to the user's browser. When someone visits /dashboard, Next.js runs the page's Server Components on the server, converts their output to HTML, and sends that HTML to the browser.

Request: GET /dashboard │ ▼ ┌─────────────────────────────────┐ │ SERVER │ │ │ │ DashboardPage.tsx │ │ ├─ queries the database │ │ ├─ checks auth session │ │ └─ renders HTML │ │ │ │ ProfileBanner, StatsBar, │ │ RecentActivity all run here │ └─────────────────────────────────┘ │ HTML arrives in browser ▼ ┌─────────────────────────────────┐ │ BROWSER │ │ │ │ CompanyResearchChart │ │ JobsFoundChart │ │ MatchScoreChart │ │ (these run here — they need │ │ the DOM to draw SVG charts) │ └─────────────────────────────────┘

Because DashboardPage is a Server Component, it can do something a browser component cannot: read the database directly. No API call needed — the page function just awaits the query. That's why the profile banner (which checks whether is_complete is true in the database) can work without a separate network request from the browser.

What "use client" actually marks

The directive "use client" at the top of a file is not a description — it is a boundary declaration. It says: "this file, and everything it imports, should be included in the JavaScript bundle sent to the browser."

Look at the first three lines of CompanyResearchChart.tsx:

"use client";

import {
  BarChart,
  Bar,
  XAxis,
  YAxis,
  CartesianGrid,
  ResponsiveContainer,
} from "recharts";

The "use client" marks this file as a client entry point. Recharts and all of its dependencies become part of the JavaScript that downloads to the user's browser. That JavaScript runs in the browser and uses the DOM to draw the SVG chart.

Without "use client", Next.js would try to run recharts on the server — where there is no DOM, no window, no ResizeObserver. It would throw an error at build time.

The rule in one sentence: Add "use client" to a file only when that file (or something it imports) needs browser APIs — window, document, ResizeObserver, useState, event handlers. If it just renders HTML from props, leave it as a Server Component.

Why this split matters for data

The server/client split creates two very different ways of getting data onto the page:

Server Components get data directly from the source. DashboardPage awaits an InsForge query in the same function that returns the JSX. No API route, no useEffect, no loading spinner. The HTML arrives pre-populated.

Client Components must get data through a network boundary. If a Client Component needs data, it has to fetch it from an API route after the browser loads. That means a loading state, a spinner, and at least one round-trip to the server after page load.

In the dashboard, this is why the profile banner check — a real database read — lives in the Server Component page, not in ProfileBanner.tsx itself. Moving the query to a Server Component eliminates the loading state entirely. The banner is either there or not when the HTML arrives.

Common mistake: Adding "use client" to a file that doesn't need it — for example, because it "looks interactive." This unnecessarily sends code to the browser and prevents the file from using server-only features like direct DB access. When in doubt, don't add it.

Quiz — check your understanding

3. You add a new component MatchScoreGauge.tsx that displays the user's average match score as a dial. It uses useState to animate the dial on mount. Does it need "use client"?

Try it in the real codebase

Open components/dashboard/StatsBar.tsx. Confirm: no "use client" at the top. Now open components/dashboard/CompanyResearchChart.tsx. Confirm: "use client" is the first line.

Now open app/dashboard/page.tsx. Find the two lines that query the database:

const { data: profileData } = await insforge.database
  .from("profiles")
  .select("is_complete")
  .eq("id", authData.user.id)
  .maybeSingle();

This await runs on the server. The profile data arrives before the browser sees any HTML. There is no loading state, no spinner, and no API route needed for this check. That is the practical benefit of Server Components.

One thing to tell a client: "The dashboard page queries the database on the server before it sends anything to your browser. By the time your browser receives the page, the data is already baked in — that's why there's no loading spinner on the profile banner."

Hint
Three files have "use client" — the three that import recharts. recharts uses ResizeObserver internally for ResponsiveContainer, which is a browser API. Server Components run in Node.js, which has no DOM and no ResizeObserver.
Exercise 2 Break & fix

Remove "use client" from components/dashboard/CompanyResearchChart.tsx. With npm run dev running, reload http://localhost:3000/dashboard. Read the error message carefully — it names exactly which browser API recharts tried to use.

Write down the error message in your notes, then restore "use client" before continuing.

Hint
Look for "You're importing a component that needs…" in the error. Next.js is specific about which API caused the failure. recharts' ResponsiveContainer calls ResizeObserver — a browser object that doesn't exist in Node.js. The error tells you exactly what to fix and why.
