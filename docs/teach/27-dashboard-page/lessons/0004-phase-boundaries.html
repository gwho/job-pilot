Lesson 4 of 4

Phase boundaries and data contracts

How the dashboard moves from mock to real data — and what this teaches about data pipelines

⏱ ~20 min 📘 Tutorial 27, Parts 1 & 2 + Explanation §1–2 🎯 Features 14 → 15 → 16 → 17

Why this lesson matters for your mission: The four dashboard features (14–17) are a mini data pipeline: UI layer → database metrics → event logs → analytics. Every real data dashboard follows this same pattern. Understanding how the phases are separated — and why — gives you a mental model for describing any data project: what data lives where, who transforms it, and what contract each layer must meet.

The four phases of the dashboard

The dashboard doesn't get fully wired in one feature. It is built in deliberate phases:

Feature What becomes real Data source
14 — UI Profile banner only profiles table
15 — Stats 4 stat cards jobs, agent_runs tables
16 — Activity Recent activity list agent_runs table
17 — Charts 3 analytics charts PostHog event API

Each phase introduces a new data source with a different character:

  • Database rows (Features 15, 16) — structured, queryable, owned by the application. Count rows, filter by date, join tables.
  • Analytics events (Feature 17) — time-series event stream, owned by a third party (PostHog). Aggregate events, bucket by day, filter by event name.

The data contract: what each component is promised

A "data contract" is the shape a component is promised it will receive. In TypeScript, the contract is the prop type. In the dashboard, every component's contract is visible in its type definition.

Open components/dashboard/StatsBar.tsx and find the exported type:

export type StatCardConfig = {
  label: string;
  value: string;
  trend?: { value: string; label: string };
  subtitle?: string;
};

This is the contract. Feature 15 must produce an array of objects that satisfy this shape. The database query result — whatever form it takes — must be transformed to match before being passed to StatsBar. The component never knows whether those strings came from a database or a constant in page.tsx.

Similarly, ActivityItem in RecentActivity.tsx is the contract for Feature 16:

export type ActivityItem = {
  type: "search" | "research";
  label: string;
  timeAgo: string;
};

Feature 16 will query agent_runs, transform each row into this shape (computing timeAgo from a timestamp, mapping run type to "search" or "research"), and pass the result as the items prop. The RecentActivity component file never opens.

Transformation: the gap between raw data and the contract

Raw data rarely matches the contract directly. There is always a transformation step between "what the data source produces" and "what the component accepts."

Data source Transformation Component ──────────────── ────────────────── ────────────────────── agent_runs table Query + map in RecentActivity { page.tsx receives: id, ──────────────────► [ run_type: "search", { type: "search", { type, label, created_at, label: "Found N timeAgo } jobs_found: 8, jobs for X", ] query: "Frontend timeAgo: "2h ago" } Engineer", } }

The transformation lives in page.tsx — not in the component, and not in a separate "adapter" file. This keeps the component pure (it just renders) and makes the transformation visible in the same file that controls data flow.

PostHog events: a different kind of data source

Features 15 and 16 use database rows — the same data model that the rest of the app writes and reads. Feature 17 uses PostHog events, which are a different kind of data: an immutable, append-only log of things that happened.

When a user runs a job search, job_found events fire (one per job discovered). PostHog stores these events. Feature 17 will query PostHog to get: "how many job_found events fired on each day of the last 7 days?" That produces a time-series — a count per day — which maps directly to the chart's contract:

// PostHog query result (simplified)
[
  { date: "2024-01-08", count: 15 },
  { date: "2024-01-09", count: 32 },
  // ...
]

// Transformation (rename "date" to "day", format date)
[
  { day: "Mon", count: 15 },
  { day: "Tue", count: 32 },
  // ...
]

// Chart contract
{ day: string; count: number }[]  ✓

The contract was designed in Feature 14 with this transformation in mind. The mock array is the proof: it already has the transformed shape. Feature 17 doesn't need to redesign anything — it just needs to produce the same shape from real data.

The general pattern: Design the output shape (the contract) first. Mock it. Then, when the real data source is ready, write a transformation that produces that shape. The component never changes; the contract is the stable anchor that both sides converge on.

What this means for explaining a dashboard to someone

When someone asks "where does this number come from?" the answer is always one of these layers:

  1. The database — rows in a table. "284 jobs found" is a COUNT(*) on the jobs table for this user.
  2. The event log — things that happened. "Company Research Activity" is a count of company_researched PostHog events per day.
  3. The application log — run records. "Recent Activity" is the last 5 rows from agent_runs, formatted as human-readable text.

Each section of a dashboard maps to one of these sources. When you can identify the source for each section, you can describe the full data pipeline — from user action to chart — to anyone who needs to understand it.

2. The chart contract is { day: string; count: number }[]. Feature 17's PostHog query will return dates as ISO strings like "2024-01-08", not day names like "Mon". Who is responsible for this transformation?

3. What is the practical difference between the data sources for Feature 15 (stat cards) and Feature 17 (charts)?

The full pipeline you just learned

User action Data stored Dashboard section ──────────────────── ────────────────── ────────────────────────── User runs job search → agent_runs row → Recent Activity (F16) → jobs rows (N) → Total Jobs Found stat (F15) → job_found events → Jobs Found chart (F17) User researches → agent_runs row → Recent Activity (F16) company → company_researched → Company Research chart (F17) PostHog event User saves profile → profiles row → Profile banner (F14) is_complete = true disappears

Every row, every count, every chart bar has a provenance — a trail back to a specific user action stored in a specific place. When you can trace that trail, you can explain any number on the dashboard to anyone.

For freelance, portfolio, and sales admin work: This trail-tracing skill is what separates someone who "built a dashboard" from someone who "designed a data pipeline." In client conversations, you can say: "The 'Jobs Found This Week' number counts rows in the jobs table where the user_id matches and the created_at date is within the last 7 days." That kind of specificity builds trust.
