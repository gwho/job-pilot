Lesson 2 of 4

The mock data seam

Why all data lives in page.tsx — and why that decision matters for Features 15–17

⏱ ~20 min 📘 Tutorial 27, Part 1 🎯 Feature 14 → 15 → 16 → 17

Why this lesson matters for your mission: This pattern — designing a data interface before the real data source exists — is one of the most transferable skills in software. It shows up in freelance projects ("I'll wire your real CMS data later, but here's the layout now"), data engineering ("I'll define the schema first, then fill it"), and sales tools ("here's what the dashboard will look like with your actual numbers"). Understanding the seam is understanding how to separate design from data.

The problem: data sources aren't always ready

When Feature 14 was built, three future features didn't exist yet:

  • Feature 15 — real stat numbers from the database
  • Feature 16 — real activity rows from agent_runs
  • Feature 17 — real chart data from PostHog analytics

The dashboard UI needed to be built anyway — to verify the layout, the design system, and the component structure. But what do you put in the charts when PostHog isn't wired yet? What numbers do you show in the stat cards when the database queries haven't been written?

The answer is mock data. But where that mock data lives — and what shape it takes — determines how hard or easy Features 15–17 will be.

The seam: one file controls all data

Open app/dashboard/page.tsx and look at the first 90 lines. Every piece of data the dashboard renders is defined here, at module level, before the component function:

const mockStats: StatCardConfig[] = [
  {
    label: "Total Jobs Found",
    value: "284",
    trend: { value: "+12%", label: "vs last week" },
  },
  // ...
];

const mockActivity: ActivityItem[] = [
  { type: "search", label: "Found 8 jobs for Frontend Engineer", timeAgo: "10 mins ago" },
  // ...
];

const mockCompanyResearchData = [
  { day: "Mon", count: 2 },
  // ...
];

These constants are passed as props to every component that renders them:

<StatsBar stats={mockStats} />
<RecentActivity items={mockActivity} />
<CompanyResearchChart data={mockCompanyResearchData} />

The components themselves contain no data. StatsBar renders whatever it receives in stats. CompanyResearchChart renders whatever it receives in data. They don't know — and don't care — whether those values came from mock constants or a real database query.

Feature 14 (today) Feature 17 (future) ───────────────────────── ────────────────────────────────── page.tsx page.tsx │ │ ├── mockCompanyData ─────► ├── real PostHog query ────► │ [{ day, count }] │ [{ day, count }] │ │ (same shape!) ▼ ▼ CompanyResearchChart CompanyResearchChart (unchanged) (unchanged)

The swap from mock to real requires changing exactly one line: the value passed to data={...}. The component file never opens.

This is the seam. A seam is a place where you can substitute one behavior for another without editing the code at that place. page.tsx is the seam. Features 15–17 work by swapping what page.tsx passes in — not by modifying the components that receive the data.

Why the shape of mock data matters

Look at the chart mock data shape:

const mockCompanyResearchData = [
  { day: "Mon", count: 2 },
  { day: "Tue", count: 5 },
  { day: "Wed", count: 3 },
  // ...
];

This shape — { day: string; count: number }[] — was not chosen arbitrarily. It mirrors what a PostHog time-bucketed event query returns after transformation. When Feature 17 is built, the PostHog query will produce data in (roughly) this structure, which gets transformed into exactly this shape before being passed to the chart.

If the mock data had used a different shape — say { label: string; value: number }[] — the component would be built for the wrong interface. Feature 17 would have to either transform the PostHog data into the wrong shape, or change the component's prop type (a breaking change).

Designing mock data to match the eventual real data is a form of API design. You're writing a contract: "this is what the component will accept, and this is what the data source must produce."

Module level vs. inside the function

Notice that the mock constants are declared at module level — outside the DashboardPage() function. This is deliberate.

A Server Component page function runs on every HTTP request. If mockStats were declared inside DashboardPage(), a new array would be allocated in memory on every page visit. The content would be identical, but the allocation is unnecessary work for data that never changes between requests.

Module-level constants are created once when the file is loaded, then reused on every request. For mock data, this is always the right location. For real data (data that depends on the authenticated user), it must be inside the function — because it changes per request.

Try it in the real codebase

Open components/dashboard/CompanyResearchChart.tsx. Notice: no internal data, no imports from any data source. The entire file is a pure rendering function that takes a data prop and draws a chart.

Now open app/dashboard/page.tsx and find line 116:

<CompanyResearchChart data={mockCompanyResearchData} />

This is the seam. Feature 17 changes this one prop value. The chart component, its imports, its type definitions — all unchanged.

One thing to tell a client or portfolio reviewer: "The charts are built with placeholder data right now, but the component API is already designed to accept real analytics data. Wiring the real data is a targeted change in one file — not a rebuild of the chart components."

Exercises

Exercise 1 Modify

In app/dashboard/page.tsx, add a 6th item to mockActivity:

{ type: "research", label: "Researched Anthropic", timeAgo: "3 days ago" }

Save and reload http://localhost:3000/dashboard. Count the activity rows. The new item should appear without touching RecentActivity.tsx. That's the seam: the prop is the only channel between data and display.

Hint
The type field must be exactly "search" or "research". TypeScript will show an error if you use anything else — because ActivityItem.type is a union type "search" | "research", not a plain string. This is the type contract enforcing correctness at the seam boundary.
Exercise 2 Trace

In app/dashboard/page.tsx, move mockActivity from module level (outside DashboardPage()) to inside the function body — just below the const userId line. The dashboard should render identically.

Now answer in your notes: on 1,000 simultaneous requests, how many array allocations happen for each version? Which is correct for static data — and why?

Undo the change before moving to Lesson 3.

Hint
Module-level: the array is created once when Node.js loads the file. All 1,000 requests share that one reference. Inside the function: a new array is allocated on every call — 1,000 requests, 1,000 allocations. For data that never changes between requests, module-level is always the right location.
