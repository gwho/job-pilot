1
URL as View State

Primary source: Next.js useSearchParams docs · Linking and Navigating guide

The problem that forced this decision

Before Feature 11, filter state lived in useState inside FindJobsClient. This worked fine until you thought about Feature 12, which adds row-click navigation to job detail pages.

Imagine this: a user filters to "High Match", navigates to page 3, finds a job they like, clicks it, reads the detail page, presses back. Where do they land?

With useState: page 1, no filter applied. The state was destroyed when they navigated away. React does not save component state across navigation — it mounts the component fresh every time it appears.

With URL: the browser restores the exact URL the user was on. useSearchParams() reads ?match=high&page=3 and the table renders exactly as the user left it.

How useSearchParams() works

Open FindJobsClient.tsx and find lines 44–52:

const searchParams = useSearchParams();
const router = useRouter();
const pathname = usePathname();

// View state — derived from URL on every render
const match = parseMatch(searchParams.get("match"));
const sort  = parseSort(searchParams.get("sort"));
const page  = parsePage(searchParams.get("page"));
const q     = parseQ(searchParams.get("q"));

useSearchParams() is reactive. That word means: when the URL changes — from any source, including the browser back button — this hook triggers a re-render. The component reads the new values automatically. You do not need a useEffect to watch for URL changes.

Notice there is no useState for any of these four values. They are derived from the URL on every render. There is only one source of truth.

Parse helpers: why they exist

The URL is a string. A user could type ?match=banana in the address bar. The parse helpers in lib/find-jobs-utils.ts coerce any invalid value to a sensible default silently:

export function parseMatch(raw: string | null): MatchFilter {
  return (["all", "high", "low"] as const).includes(raw as MatchFilter)
    ? (raw as MatchFilter)
    : "all"; // anything invalid becomes "all"
}

The pattern is the same for all four: if the value is valid, use it; if not, use the default. The tests in utils.test.ts verify all the edge cases — null, empty string, wrong capitalisation, nonsense strings.

Why Suspense is required

Add useSearchParams() to a component and Next.js App Router requires that component to be wrapped in <Suspense>. Without it, the build fails. Open app/find-jobs/page.tsx:

<Suspense fallback={null}>
  <FindJobsClient initialJobs={(jobs as Job[]) ?? []} />
</Suspense>

fallback={null} — not a spinner, not a skeleton — because the Server Component (FindJobsPage) already fetched the jobs and delivered the rendered HTML before the client hydrates. There is no loading state to show. A spinner would flash briefly and vanish, which is worse than nothing.

Retrieval check — Part 1

A user is on /find-jobs?match=high&page=3, clicks a job row, and presses the browser back button. With URL state, what does the URL look like when they land back on Find Jobs?

Reveal answer

/find-jobs?match=high&page=3 — exactly as they left it. The browser restores the URL from the history entry. useSearchParams() reads it. The table renders with "High Match" filter and page 3 active. Nothing was lost.

2
replace() vs push()

Primary source: Next.js useRouter docs · MDN History API

The browser history stack

Your browser keeps a stack of visited URLs. Every tab has one. A "stack" is like a pile of cards — you can add to the top, go back one step, or go forward one step. You cannot jump to the middle.

Two methods change this stack differently:

MethodWhat it does to the stack
router.push(url)Adds a new card on top. Back goes to the previous card.
router.replace(url)Replaces the current card in place. Back goes to what was before this card.

Why filter changes must use replace()

Imagine the user does this on Find Jobs, and every filter change uses push():

  1. Loads /find-jobs — stack: [/find-jobs ←]
  2. Sets match to "High" — stack: [/find-jobs, /find-jobs?match=high ←]
  3. Changes sort to "Newest" — stack: [/find-jobs, ?match=high, ?match=high&sort=newest ←]
  4. Clicks a job — stack: [/find-jobs, ?match=high, ?match=high&sort=newest, /find-jobs/42 ←]
  5. Presses back → lands on ?match=high&sort=newest ✓
  6. Presses back → lands on ?match=high — still on Find Jobs 🚫
  7. Presses back → lands on /find-jobs — still on Find Jobs 🚫
  8. Presses back → finally leaves Find Jobs

Four back-presses to leave a page the user visited once. With replace(), steps 2 and 3 both overwrite the same card. The stack stays at two entries: Find Jobs + the job detail. Two back-presses, the second of which leaves.

The replaceViewState helper

All filter/sort/page changes in FindJobsClient go through one function — replaceViewState. It reads the current params, applies the updates, and calls router.replace():

function replaceViewState(updates: {
  q?: string; match?: MatchFilter; sort?: Sort; page?: number
}) {
  const params = new URLSearchParams(searchParams.toString()); // copy current
  if ("q" in updates) {
    if (updates.q) params.set("q", updates.q);
    else params.delete("q"); // empty string removes the param entirely
  }
  if ("match" in updates) params.set("match", updates.match!);
  if ("sort"  in updates) params.set("sort",  updates.sort!);
  if ("page"  in updates) params.set("page",  String(updates.page));
  router.replace(`${pathname}?${params.toString()}`);
}

Notice that it copies the current params first (new URLSearchParams(searchParams.toString())). Changing the sort does not erase the current match filter. Each update is surgical — only the specified keys change.

The rule

Use replace()

Refining the same view — filter, sort, page, text search. The user is adjusting how they see this data, not going to a new page.

Use push()

Navigating to a different page — clicking a job row (Feature 12). The user is going somewhere new and should be able to come back from it with one back-press.

Retrieval check — Part 2

A "Reset all filters" button calls replaceViewState({ match: "all", sort: "score", page: 1, q: "" }). Should it use replace() or push()? And will pressing back after clicking it restore the old filters?

Reveal answer

replace() — resetting filters is a refinement of the same view, not navigation to a new page. And no, pressing back will not restore the old filters — replace() overwrites the current history entry. To make "undo reset" work you would need push(), but that adds an unwanted back-button stop. The standard choice for filter resets is replace(); undo is not expected.

3
Two Pieces of State for One Input

Primary source: React useEffect docs · You Might Not Need an Effect

The problem: you cannot control a text input from the URL directly

If the text filter input read directly from the URL param and called router.replace() on every keystroke, typing the word "react" would fire five URL updates: r, re, rea, reac, react. Each triggers a re-render cycle. The input would feel laggy or broken — characters would appear out of order or with visible delay.

The solution: split into display state and view state

Feature 11 separates these concerns into two completely independent pieces of state:

NameStored inUpdates whenDrives
filterTextDraft useState Every keystroke — instant The visible input value
URL q param useSearchParams() 300ms after typing stops The actual filter in useMemo

The input shows the draft. The filter uses the URL. They are decoupled. The user sees instant typing. The filter updates feel almost instant (300ms is imperceptible for filtering).

The two useEffects — read carefully

Find these in FindJobsClient.tsx around lines 64–83:

// Effect 1 — sync URL → draft  (back/forward navigation)
useEffect(() => {
  // eslint-disable-next-line react-hooks/set-state-in-effect
  setFilterTextDraft(q);
}, [q]);

// Effect 2 — debounce draft → URL  (typing)
useEffect(() => {
  if (filterTextDraft === q) return;  // <-- the guard
  const timeout = window.setTimeout(() => {
    replaceViewState({ q: filterTextDraft, page: 1 });
  }, 300);
  return () => window.clearTimeout(timeout);
}, [filterTextDraft]);

Effect 1 runs when q (the URL param) changes. The only time q changes without the user typing is back/forward navigation. When the browser restores ?q=react, Effect 1 fires and resets the input to show "react".

Effect 2 runs when filterTextDraft changes — i.e., when the user types. It waits 300ms and then writes to the URL. The cleanup function (return () => clearTimeout(...)) cancels the timer if the user types again before 300ms is up — so only the final keystroke triggers a URL update.

Why the guard is required

The line if (filterTextDraft === q) return in Effect 2 is what prevents an infinite loop. Without it:

  1. Back-nav changes URL to ?q=react
  2. Effect 1 fires → sets filterTextDraft = "react"
  3. Effect 2 fires (because filterTextDraft changed) → calls replaceViewState({ q: "react" })
  4. URL changes → Effect 1 fires again → loop continues forever
With the guard: at step 3, Effect 2 checks filterTextDraft === q. Both are "react". The check is true. It returns immediately. No URL update fires. No loop.

What the filter actually uses

The useMemo filter pipeline uses q (from the URL), not filterTextDraft. This is intentional. The filter only changes when the URL changes — after the debounce settles — not on every keystroke.

if (q.trim()) {
  const lower = q.toLowerCase();
  result = result.filter(
    (j) =>
      j.company?.toLowerCase().includes(lower) ||
      j.title?.toLowerCase().includes(lower),
  );
}

Retrieval check — Part 3

The user types "node" into the text filter, waits 400ms (so the URL updates to ?q=node), then immediately presses the browser back button (restoring ?q=react from the previous history entry). What does the text input show, and what does the filter use, immediately after the back button is pressed?

Reveal answer

The URL is now ?q=react. Effect 1 fires and sets filterTextDraft = "react". The text input immediately shows "react". The useMemo filter reads q = "react" from the URL. Both the visible input and the filter now show "react". The guard in Effect 2 prevents any replace loop because filterTextDraft === q is true.

Merging Jobs After Search

Primary source: React useState — functional updates · MDN Map

The bug that existed before Feature 11

The original handleSearch did this after a search returned:

setJobs(data.jobs); // <-- BUG: replaces ALL history

If a user ran two searches — "Senior React Developer" then "React Engineer" — they could only see jobs from the second search. All jobs from the first search were gone.

The merge fix

The fixed version in lib/find-jobs-utils.ts:

export function mergeJobsById<T extends { id: string }>(
  current: T[],
  incoming: T[],
): T[] {
  const merged = new Map(current.map((job) => [job.id, job]));
  for (const job of incoming) {
    merged.set(job.id, job); // newer data wins on id collision
  }
  return [...merged.values()];
}

Step by step:

  1. Turn the current jobs into a Map keyed by id. A Map cannot have duplicate keys — this is the deduplication mechanism.
  2. Loop through the incoming (new) jobs. For each one, merged.set(job.id, job) either adds a new job or overwrites an existing one with the same id — newer data wins.
  3. Convert the Map back to an array with [...merged.values()].

Jobs from previous searches are preserved. Jobs in both searches are deduplicated. Freshly scored jobs replace their unscored versions.

Why the functional form matters

In FindJobsClient.tsx, the call is:

setJobs((currentJobs) => mergeJobsById(currentJobs, data.jobs as Job[]));

The key is (currentJobs) =>. This is the functional form of state update. React guarantees that currentJobs is the actual current state when the setter runs — regardless of what else happened since handleSearch started.

The closure form would be: setJobs(mergeJobsById(jobs, data.jobs)). Here jobs is captured from the outer scope at the time handleSearch was called. If two searches overlap — the second starts before the first finishes — the second search's closure has a stale jobs array. It would overwrite whatever the first search already wrote.

Rule: whenever a state update depends on the previous value of that state, always use the functional form setState(prev => ...).

Why router.refresh() would not have worked

router.refresh() re-runs the Server Component and passes fresh initialJobs as a prop to FindJobsClient. But useState(initialJobs) only uses its argument on the first render — the mount. After that, React ignores prop changes to the initial value. Calling router.refresh() updates the prop but the state stays unchanged.

To make it work you would need useEffect(() => setJobs(initialJobs), [initialJobs]) — which is an anti-pattern (effect syncing props to state) and also causes a visible flash as the list jumps to the server data after already showing the merged result.

Retrieval check — Part 4

You have 10 jobs from a first search. You run a second search that returns 5 jobs — 2 are new, 3 are the same as before (same id) but now have a match_score that was null before. After the merge, how many total jobs are in the array?

Reveal answer

12 jobs. 10 original + 2 brand new = 12. The 3 overlapping jobs (same id) are overwritten in place — the Map deduplicates them. The Map starts with 10 entries (from current), then 5 sets run (2 add new entries, 3 overwrite existing ones). Final Map has 12 entries. The 3 overwritten jobs now have match scores.

Null Score Semantics

Primary source: MDN Equality comparisons · CONTEXT.md (domain definitions)

What an unscored job is

When the Apify actor discovers a job but the AI matcher has not yet run (or failed), the database stores match_score IS NULL. This is not a 0% match. It is "unknown." The job was found; it has not been evaluated yet.

The ?? 0 trap

// Wrong
const score = job.match_score ?? 0;
result.filter(j => j.match_score < MATCH_THRESHOLD); // includes nulls-as-zero

Nullish coalescing (?? 0) turns every unscored job into a 0% match. The filter then puts them in "Low Match." If the user switches to "High Match" or "Low Match," unscored jobs vanish completely from view. They are effectively hidden in a category where they do not belong.

The correct approach: explicit null check

// High Match — exclude null explicitly
result.filter(j => j.match_score != null && j.match_score >= MATCH_THRESHOLD)

// Low Match — exclude null explicitly
result.filter(j => j.match_score != null && j.match_score < MATCH_THRESHOLD)

// All Matches — no filter; null scores appear here

Unscored jobs only appear in "All Matches" — the default view. They are never in High or Low. In the score cell, they show a neutral dash:

{job.match_score != null ? (
  <MatchScoreBar score={job.match_score} />
) : (
  <span className="text-sm text-text-muted">—</span>
)}

!= null vs !== null

Notice the check is != null (double equals, loose), not !== null (triple equals, strict).

CheckCatchesMisses
!== nullnullundefined
!= nullBoth null and undefinednothing relevant

TypeScript says the type is number | null, but JavaScript at runtime can produce undefined for optional fields — for example, when the JSON from the API omits the field entirely rather than setting it to null. The loose check is defensive and costs nothing.

Retrieval check — Part 5

A job has match_score: null. The user's current filter is "Low Match". Does the job appear in the table? Why?

Reveal answer

No. The Low Match filter is j.match_score != null && j.match_score < MATCH_THRESHOLD. The first condition (j.match_score != null) is false for this job. Short-circuit evaluation means the second condition is never checked. The job is excluded from Low Match entirely. It would only appear if the user switches to "All Matches."

Windowed Pagination

Primary source: React useMemo docs · lib/find-jobs-utils.ts

The naive approach and its failure

A simple pagination bar might show:

[1] [2] [3] [...] [20]

If the user is on page 10, they have no idea where they are. They see pages 1, 2, 3, and 20 — but not 10. They cannot tell if they are near the beginning or middle. This is the naive approach that existed before Feature 11.

The windowed algorithm

The goal: always show page 1, the last page, the current page, and the pages immediately before and after the current page. Fill gaps with "...".

Open lib/find-jobs-utils.ts and find buildPageNumbers:

export function buildPageNumbers(
  totalPages: number,
  safePage: number,
): (number | "...")[] {
  // If 5 or fewer total pages, just show them all
  if (totalPages <= 5) {
    return Array.from({ length: totalPages }, (_, i) => i + 1);
  }

  // Collect the pages that should always be visible
  const neighbours = new Set(
    [1, totalPages, safePage, safePage - 1, safePage + 1]
      .filter(p => p >= 1 && p <= totalPages) // clamp to valid range
  );

  // Sort them ascending
  const sorted = [...neighbours].sort((a, b) => a - b);

  // Walk through and insert "..." wherever there is a gap
  const result: (number | "...")[] = [];
  for (let i = 0; i < sorted.length; i++) {
    if (i > 0 && sorted[i] - sorted[i - 1] > 1) result.push("...");
    result.push(sorted[i]);
  }
  return result;
}

Walking through an example

Current page: 10. Total pages: 20.

  1. Build the Set: {1, 20, 10, 9, 11}
  2. Sort it: [1, 9, 10, 11, 20]
  3. Walk and insert gaps:
    • 1 → add 1
    • 9 — gap of 8 from 1 → add "...", then 9
    • 10 — gap of 1 from 9 → no gap, add 10
    • 11 — gap of 1 from 10 → no gap, add 11
    • 20 — gap of 9 from 11 → add "...", then 20
  4. Result: [1, "...", 9, 10, 11, "...", 20]

The user can see they are on page 10, near the middle. They can jump to 9, 11, 1, or 20 with one click.

safePage: clamping to avoid an empty screen

In FindJobsClient.tsx:

const safePage = Math.min(page, totalPages);

If a user is on page 5 and switches from "All Matches" (40 jobs, 2 pages) to "High Match" (8 jobs, 1 page), page from the URL is still 5 but totalPages is 1. safePage clamps to 1. The slice uses safePage, so the user sees the last valid page instead of an empty table.

PAGE_SIZE has one owner

PAGE_SIZE = 20 is defined in FindJobsClient (which slices the array) and passed as a prop to JobsPagination (which shows the "Showing X to Y of Z" label).

Before Feature 11, JobsPagination had its own independent const PAGE_SIZE = 6. The slice showed 20 jobs per page but the label said "Showing 1 to 6 of 42." TypeScript never caught this — both constants were just numbers. The only way to catch it would have been a test or a visual inspection.

Rule: the component that performs a computation owns the constant that governs it. Other components that only display derived values receive it as a prop.

Retrieval check — Part 6

Call buildPageNumbers(20, 2) by hand. What does the returned array look like, and how many "..." entries does it contain?

Reveal answer

Set: {1, 20, 2, 1, 3} → after dedup and sort: [1, 2, 3, 20]. Walking: 1 → add 1. 2, gap 1 → add 2. 3, gap 1 → add 3. 20, gap 17 → add "...", add 20. Result: [1, 2, 3, "...", 20]. One "..." entry.
