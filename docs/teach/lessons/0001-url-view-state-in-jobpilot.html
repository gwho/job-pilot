Lesson 0001

URL View State in JobPilot

Based on Feature 11 — FindJobsClient.tsx and lib/find-jobs-utils.ts.

One tangible win: after this lesson you will be able to look at any piece of state in this codebase and decide — URL, local React state, or neither — and explain your reasoning using the actual Find Jobs code.

Why this matters for JobPilot

In Feature 12, every job row becomes clickable. A user will filter to "High Match, page 3, sorted by Newest" and click a job to read it. When they press the browser's back button, they need to land exactly back where they were — same filter, same page, same sort.

If that state lived in React's useState, pressing back would wipe it completely. React discards component state when you navigate away. The URL survives. That single fact drives most of the design in this feature.

The test that proves the parsing rules

Open __tests__/find-jobs/utils.test.ts. These tests describe exactly what happens when the URL contains garbage:

describe("parseMatch", () => {
  it("returns 'all' for null", () => {
    expect(parseMatch(null)).toBe("all");   // no ?match= in URL
  });
  it("returns 'all' for invalid strings", () => {
    expect(parseMatch("HIGH")).toBe("all"); // user typed it manually
  });
});

The function is in lib/find-jobs-utils.ts. Any URL the user types — valid or broken — is silently normalised to a sensible default. No crash. No empty screen.

The subtlest part: filterTextDraft and the two-effect guard

The text filter has a problem. If we controlled the input directly from the URL, every keystroke would call router.replace() — five URL updates to type "react". The input would feel broken.

So we split it into two pieces of state that stay in sync:

// Display state — updates on every keystroke, controls the input
const [filterTextDraft, setFilterTextDraft] = useState(q);

// Effect 1: when back-nav changes the URL, reset the input to match
useEffect(() => {
  setFilterTextDraft(q);
}, [q]);

// Effect 2: when the user types, write to URL after 300ms
useEffect(() => {
  if (filterTextDraft === q) return; // <-- guard: prevents a loop
  const timeout = window.setTimeout(() => {
    replaceViewState({ q: filterTextDraft, page: 1 });
  }, 300);
  return () => window.clearTimeout(timeout);
}, [filterTextDraft]);

Without the guard if (filterTextDraft === q) return, pressing back would create an infinite loop: the URL changes → Effect 1 sets the draft → Effect 2 fires → writes to URL → Effect 1 fires again. The guard breaks the cycle because after Effect 1 runs, the draft and the URL are the same, so Effect 2 immediately returns.

router.replace() not router.push()

Every filter/sort/page change calls router.replace(). Imagine if we used push() instead — every filter tweak would add a new back-button step. After five filter changes you would need six back-presses to leave Find Jobs. replace() means "update the current history entry," so the user always has exactly one back-press to leave.

Use replace()

Changing filter, sort, or page. Still the same screen, different view of the same data.

Use push()

Clicking a job row (Feature 12). Going to a genuinely different page that should get its own back-button entry.

Retrieval check 1 — state placement

In Feature 12 you add a "Selected job" panel. The currently selected job ID is needed to highlight the row. Where should it live?

Reveal answer

URL. It describes "what I am looking at." The user should be able to share a link to a specific job row, or press back from the detail page and see it highlighted. This is the same rule as match and page.

Retrieval check 2 — the guard

You remove the if (filterTextDraft === q) return line from the debounce effect. The user presses the browser back button to restore ?q=react. What happens next?

Reveal answer

Infinite loop. Back-nav changes the URL → Effect 1 sets filterTextDraft = "react" → Effect 2 fires because filterTextDraft changed → replaceViewState({ q: "react" }) runs → URL changes → Effect 1 fires again. Without the guard the cycle never stops.

Retrieval check 3 — predict the test output

Without looking at the code, what will parsePage("-1") return? What about parsePage("1.5")?

Reveal answer

Both return 1 — the default. -1 is not a positive integer. 1.5 fails the Number.isFinite(n) && n > 0 check because parseInt("1.5") returns 1 — actually that would return 1, not the default. Check the real test in utils.test.ts to verify — the test exists precisely to make you look.

Code-tracing exercise

Trace this user action through the real files without running the app:

  1. User is on /find-jobs?match=high&page=3
  2. User types "react" in the text filter input

Answer: what does the URL look like after step 3? Which exact line of code changes it?

Reveal answer

/find-jobs?match=high&page=1&q=react. The page resets to 1 (new search context). The code that runs is the debounce setTimeout callback inside the second useEffect in FindJobsClient.tsx, which calls replaceViewState({ q: filterTextDraft, page: 1 }).
