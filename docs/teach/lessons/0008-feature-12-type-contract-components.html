Lesson 0008

Feature 12 — The Type Contract and Component Architecture

Goal: understand how the Job interface's nullable fields drive UI rendering decisions, why the page decomposes into exactly five components, and why Feature 12 is intentionally read-only. Series: Feature 12 Deep Dive (2 of 4).

1 — The Job interface as a UI contract

Open types/index.ts, lines 117–142. The Job interface is the contract between the database and every component on the detail page.

export interface Job {
  id: string
  run_id: string | null
  user_id: string
  source: JobSource
  source_provider: JobProvider | null
  source_url: string | null         // ← null → hide "View Job Post" button
  external_apply_url: string | null // ← null → Apply Now falls back to source_url
  title: string | null
  company: string | null
  location: string | null           // ← null → show "—" in info card
  salary: string | null             // ← null → show "—" in info card
  job_type: JobType | null          // ← null → show "—", not "Full-time"
  about_role: string | null         // ← null → "No description available."
  responsibilities: string[] | null // ← not displayed in Feature 12
  requirements: string[] | null     // ← not displayed in Feature 12
  nice_to_have: string[] | null     // ← not displayed in Feature 12
  benefits: string[] | null         // ← not displayed in Feature 12
  about_company: string | null      // ← not displayed in Feature 12
  match_score: number | null        // ← null → hide badge entirely
  match_reason: string | null       // ← null → hide reasoning card entirely
  matched_skills: string[] | null   // ← null/empty → hide "You have" section
  missing_skills: string[] | null   // ← null/empty → hide "Gap skills" section
  company_research: CompanyResearchDossier | null // ← always null in Feature 12
  found_at: string                  // ← always present, used in info card
}

Notice how many fields are | null. This is not accidental — it reflects the reality of scraped job data. JobsDB does not always list salary. The AI model may not always produce a match reason. A job discovered before the scorer ran will have null match_score.

Every nullable field forces a UI decision: show a fallback, hide the element, or show an empty state. That decision is driven by the Job interface — the type is the spec.

Review question to ask: For every field the plan renders, is the field nullable in types/index.ts? If yes — does the plan specify what to show when it's null? A plan that renders {job.salary} without a null fallback is missing a specification.

The job_type trap

job_type is typed as JobType | null, where JobType = 'fulltime' | 'parttime' | 'contract'.

A common mistake: show "Full-time" when job_type is null (treating null as a default). The correct rule: null means unknown, not full-time. A user making a decision about a role based on a fabricated default is misled.

Open components/job-details/JobInfo.tsx, lines 13–18:

function formatJobType(t: string | null): string {
  if (t === "fulltime") return "Full-time";
  if (t === "parttime") return "Part-time";
  if (t === "contract") return "Contract";
  return "—";       // null OR unrecognised string → dash
}

The function returns "—" for null. It never returns "Full-time" as a default.

Retrieval check: The find route converts scraped text to JobType before saving. If "full time" was found on the page, it becomes 'fulltime'. So when would job_type be null?
When the actor's scraper found no job type information on the listing page at all — the field was absent or unreadable. The find route only converts values it received; if the actor returned null for that field, the route saves null. A null in the DB means "we did not collect this information," not "the job is full-time by default."

2 — The five-component decomposition

Open context/architecture.md and find the components/ section. The architecture doc pre-defines the decomposition:

components/
  job-details/
    JobInfo.tsx         → header card + 4-column info row
    MatchScore.tsx      → AI reasoning + skills cards
    JobDescription.tsx  → full job description card
    CompanyResearch.tsx → company research card (F13 placeholder)
    JobActions.tsx      → Apply Now button

These were planned as separate components, not as one monolithic JobDetailsContent.tsx. Why?

ComponentWhy separate
JobInfoOwns the header + info grid. Distinct visual block. Will always render. Contains display-only helpers (formatJobType, matchBadgeClasses).
MatchScoreTwo conditional cards (reasoning + skills). Conditional rendering logic belongs in one place, not spread across a larger file.
JobDescriptionSingle card with specific CSS requirement (whitespace-pre-line). Isolated from other text rendering.
CompanyResearchFeature 13 will replace this with a Client Component that has onClick. Keeping it isolated means Feature 13 edits one file, not a 200-line component.
JobActionsThe apply button has its own URL logic (externalApplyUrl ?? sourceUrl) and two distinct render paths (link vs disabled button). Isolated.

Notice the last row: CompanyResearch is intentionally isolated because it will change in Feature 13. Good component decomposition anticipates where future changes will happen and draws the boundary there.

The component path: components/job-details/, not components/find-jobs/job-details/

The route lives under app/find-jobs/[id]/. A developer might expect the components to live under components/find-jobs/. They don't. They live at components/job-details/ — a top-level sibling of components/find-jobs/.

The architecture doc defines this explicitly. The reason: routes can be restructured (move to /jobs/[id], add a route group) without touching components. If components were nested under the route path, a route refactor would require moving components. Separating them means route and component directories evolve independently.

Review question to ask: Does the plan put new components under the route path (e.g., components/find-jobs/job-details/)? Check architecture.md — if the architecture doc defines the folder, use it. Don't create a new one.
Retrieval check: All five components are Server Components. What does that mean for the browser's JavaScript bundle?
Server Components render on the server and send HTML to the browser. Their code is never sent as JavaScript to the client. This means the browser downloads no JavaScript for these components — zero bundle cost. They receive props from the page Server Component and return HTML. Adding "use client" to any of them would push their code into the browser bundle for no reason, since they have no event handlers, state, or browser API usage.

3 — Read-only scope: what Feature 12 does not do

Feature 12 is deliberately limited to display only. This is captured in the plan file (docs/plan/12-job-details-page/plan.md):

"No agent calls, no mutations — this is a read-only display feature."

Specifically, Feature 12 does NOT:

What is absentWhy absentWhere it belongs
Agent calls (Browserbase / Stagehand) No company research triggered yet Feature 13 — Company Research Agent
DB mutations (UPDATE / INSERT) Page only reads the existing job row Server Actions in actions/ — not applicable here
PostHog events No trackable user action occurs on page load Feature 13 fires company_researched when research runs
Wired "Research Company" button Research Company is a placeholder (disabled button) Feature 13 upgrades CompanyResearch.tsx to a Client Component
company_research JSONB field rendering Always null in Feature 12 Feature 13 renders the dossier after research completes

The CompanyResearch component illustrates this boundary clearly. Open components/job-details/CompanyResearch.tsx:

export function CompanyResearch({ company }: Props) {
  return (
    <div className="bg-surface border border-border rounded-2xl p-6 shadow-sm">
      <div className="flex items-center justify-between mb-6">
        ...
        {/* Feature 13 will replace this with a wired Client Component */}
        <button
          disabled
          className="... opacity-50 cursor-not-allowed"
        >
          Research Company
        </button>
      </div>
      <!-- empty state -->
    </div>
  );
}

The comment "Feature 13 will replace this" is a scope boundary marker. It says: this is as far as Feature 12 goes. The button renders, looks correct, and is visually disabled. Nothing is wired. That is correct for this feature.

Review question to ask: Does this plan wire up any functionality that isn't in scope for this feature? If the plan shows the Research Company button triggering an API call, that's scope creep. If it's disabled, that's correct. Scope boundaries prevent one feature from silently depending on another's work.
Retrieval check: Feature 12 fires no PostHog events. When should company_researched fire, and where?
company_researched should fire in Feature 13 when the research agent completes and saves the dossier to jobs.company_research. According to code-standards.md, the PostHog event table lists it as triggered when "Company research dossier generated." The API route app/api/agent/research/route.ts (Feature 13) is where it will fire — after the agent returns successfully, not on the page load in Feature 12.

4 — The job as Job type assertion

Open app/find-jobs/[id]/page.tsx, line 38:

// InsForge returns untyped query data — shape matches the jobs table Job type
const typedJob = job as Job;

InsForge's TypeScript SDK returns query results as a generic type, not a typed entity. The Job interface in types/index.ts describes the exact shape of the jobs table. The assertion tells TypeScript: treat this query result as a Job.

The code standards say: "Never use type assertions unless absolutely necessary and commented why."

The assertion is justified here because:

  • The query is .select("*") from the jobs table — all columns, no joins, no transformations
  • The Job interface was derived from the same schema (Feature 04 created both together)
  • The shape cannot diverge unless the schema changes, at which point both files must be updated

The inline comment explains why the assertion is safe. Without it, a future reader would see as Job and wonder if someone was papering over a type error.

Retrieval check: When would this type assertion become unsafe?
If the query were changed to a partial select (e.g., .select("id, title, company")) — then job would only have three fields, but the assertion would claim it has all Job fields. Accessing typedJob.match_score would return undefined at runtime while TypeScript believes it's number | null. The assertion would be masking an incompleteness. The fix would be to either select all fields (keep select("*")) or use a partial type rather than the full Job.

Summary

  • The Job interface is the UI spec — every nullable field requires a null-handling decision in the components.
  • formatJobType(null) returns "—", not "Full-time" — never invent values for null fields.
  • Five components, each with one responsibility — decomposed at the lines where future changes will happen.
  • Components live in components/job-details/ (per architecture.md), not nested under the route.
  • Feature 12 is read-only: no agents, no mutations, no PostHog events, no wired research button.
  • The job as Job assertion is safe because the query selects all columns from the table the type was derived from — and the comment says so.
