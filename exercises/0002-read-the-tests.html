utils.test.ts lines 21–23 See implementation → 
it("returns 'all' for null", () => {
  expect(parseMatch(null)).toBe("all");
});
What is this test checking? Why would null be passed to parseMatch?
Reveal answer

This checks that a missing URL parameter (no ?match= in the URL) produces a safe default. searchParams.get("match") returns null when the parameter is absent. Passing null to parseMatch simulates the first page load with no URL params. The expected return value is "all" — the default match filter.

utils.test.ts lines 25–29 See implementation → 
it("returns 'all' for invalid strings", () => {
  expect(parseMatch("medium")).toBe("all");
  expect(parseMatch("")).toBe("all");
  expect(parseMatch("HIGH")).toBe("all");
});
Why does parseMatch("HIGH") return "all" even though "high" is a valid filter? What does this tell you about how the check is written?
Reveal answer

The check uses .includes() on a fixed array ["all", "high", "low"]. JavaScript string comparison is case-sensitive. "HIGH" is not strictly equal to "high", so it is not found in the array, and the function falls back to "all". This is intentional — the URL is set programmatically by replaceViewState, which always writes lowercase values. A user manually typing ?match=HIGH in the address bar is typing something the app never generates — treat it as invalid.

utils.test.ts lines 68–75 See implementation → 
it("returns 1 for non-numeric strings", () => {
  expect(parsePage("abc")).toBe(1);
  expect(parsePage("")).toBe(1);
  expect(parsePage("1.5")).toBe(1);
});
Why does parsePage("1.5") return 1 (the default) rather than the number 1 (which would seem like a valid page)? Hint: think about what parseInt("1.5") returns in JavaScript.
Reveal answer

parseInt("1.5") returns the integer 1. Then the check is Number.isFinite(1) && 1 > 0 — both true. So actually parsePage("1.5") returns 1, the first page — not because of the fallback, but because parseInt truncates the decimal. The test is checking that the function does not crash or return NaN for decimal strings. The test comment says "non-numeric" but "1.5" is technically parseable — it just truncates to 1, which happens to be the same as the default. You can verify this by reading the implementation.

utils.test.ts lines 96–99 See implementation → 
it("returns all pages when total is 5 or fewer", () => {
  expect(buildPageNumbers(3, 2)).toEqual([1, 2, 3]);
  expect(buildPageNumbers(5, 3)).toEqual([1, 2, 3, 4, 5]);
});
Why does the algorithm have a special case for 5 or fewer pages? What would the windowed algorithm produce for buildPageNumbers(3, 2) if the special case were removed?
Reveal answer

The special case is a simplification: when there are few enough pages to show them all, the windowed logic is unnecessary overhead. Without the special case, buildPageNumbers(3, 2) would: build Set {1, 3, 2, 1, 3} → deduplicated: {1, 2, 3} → sorted: [1, 2, 3] → walk: no gaps > 1 between any adjacent numbers → result [1, 2, 3]. The same result. So the special case is an optimisation for clarity and performance, not a correction. You could remove it and the tests would still pass.

it("inserts ellipsis for gaps", () => {
  const pages = buildPageNumbers(20, 10);
  expect(pages).toContain("...");
  expect(pages.filter((p) => p === "...").length).toBe(2);
});
Without running the code, predict the full array that buildPageNumbers(20, 10) returns. Then count how many "..." entries it should have.
Reveal answer

Set: {1, 20, 10, 9, 11} → sorted: [1, 9, 10, 11, 20] → walk: 1, gap 8 to 9 → add "...", 9, 10, 11, gap 9 to 20 → add "...", 20 → [1, "...", 9, 10, 11, "...", 20]. Two "..." entries, confirming the test expectation.

utils.test.ts lines 153–159 See implementation → 
it("overwrites existing jobs with incoming data on id collision", () => {
  const current = [{ id: "a", title: "Old A" }];
  const incoming = [{ id: "a", title: "New A" }];
  const result = mergeJobsById(current, incoming);
  expect(result).toHaveLength(1);
  expect(result[0].title).toBe("New A");
});
This is the test that documents the bug that existed before Feature 11. What was the old (broken) implementation doing, and how does this test catch it?
Reveal answer

The old implementation was setJobs(data.jobs) — it replaced the entire jobs array with only the new batch. If a job with id: "a" existed from a previous search, it would be lost. More precisely for this test: the old code would have returned [{ id: "a", title: "New A" }] — which would actually pass this particular test because it checks toHaveLength(1) and title === "New A". The test that would have caught the real bug is "preserves existing jobs not in the incoming batch" (line 145) — the old code would return length 1 instead of 2 for that test.
