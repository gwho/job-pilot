Lesson 0006

What My Plan Review Opinions Mean

Goal: learn to review and criticize coding-agent plans yourself, using Feature 12 as the example.

One sentence version: a useful engineering opinion is not a preference. It is a claim about risk, backed by evidence, with a consequence for implementation.

The Three-Part Shape

When I say "I would change this," read it as three hidden parts:

Claim

This part of the plan has a property: good, risky, inconsistent, missing, or unnecessary.

Evidence

A project file, type, design rule, API contract, or user behavior proves the claim.

Consequence

If ignored, the feature may break, drift from the design, mislead users, or become harder to test.

That is why you can criticize an agent plan without being a senior engineer yet. You do not need to "feel" whether the plan is good. You need to ask: where is the claim, where is the evidence, and what happens if it is wrong?

Prerequisites You Need

To review JobPilot plans well, learn these in order:

  1. Feature scope. Know what feature number is in progress and what is intentionally deferred. For Feature 12, Company Research is visible but not wired until Feature 13.
  2. Folder ownership. Know that app/ owns pages/routes, components/ owns UI, agent/ owns agent logic, and DB queries must stay user-scoped.
  3. Server versus Client Components. Know when a component needs "use client". Event handlers and useRouter need client code; plain rendering can stay server-side.
  4. Type contracts and nullability. Know how to read types/index.ts. If Job.salary is string | null, the UI needs a null display rule.
  5. User interaction basics. Know the difference between a clickable table row and a real link. Links support keyboard navigation, browser affordances, and opening in a new tab.
  6. Verification. Know whether a test or smoke check would catch the actual failure. A check that says "Apply Now opens source_url" would miss the intended external_apply_url ?? source_url behavior.

Decode My Feature 12 Opinions

Opinion: "The plan is right to keep Feature 12 read-only."

Meaning The page should fetch and display one job. It should not run company research, score jobs again, or mutate the database.

Evidence context/build-plan.md separates Feature 12 Job Details UI from Feature 13 Company Research Agent.

Why it matters If the plan pulls Feature 13 forward, the implementation becomes harder to test and easier to break.

Opinion: "The user-scoped query is correct."

Meaning Fetching by id alone is not enough. The page must also filter by user_id.

Evidence context/code-standards.md says every DB query must be scoped to the current user.

Why it matters Without the user filter, one authenticated user could potentially access another user's saved job by ID.

Opinion: "Do not invent Full-time when job_type is null."

Meaning A null value means unknown, not full-time. The UI should show - unless the stored value says otherwise.

Evidence Job.job_type is nullable in types/index.ts.

Why it matters Invented data trains users to trust information the app does not actually have.

Opinion: "Prefer real links over only router.push on a table row."

Meaning router.push can navigate, but it does not automatically give the user all normal link behavior.

Evidence Feature 11 uses URL state so back-navigation matters; Feature 12 adds row navigation from /find-jobs to /find-jobs/[id].

Why it matters Keyboard access, open-in-new-tab, and visible link semantics are part of the real user experience.

Opinion: "Fix contradictions inside the plan before coding."

Meaning The plan correctly says Apply Now should use external_apply_url ?? source_url, but the smoke test says it opens source_url.

Evidence The same pasted plan contains both statements.

Why it matters If the verification step is wrong, the agent can implement the right code and still test the wrong behavior, or vice versa.

Your Review Algorithm

  1. Read the plan once for intent: what user-visible thing will exist when this is done?
  2. Mark every file in the plan and ask whether that folder owns that responsibility.
  3. Check data fields against types/index.ts, especially nullable fields.
  4. Check each interaction as a user: click, keyboard, back button, new tab, loading, empty state.
  5. Read the verification section and ask: would this catch the bug or drift I am worried about?
  6. Look for contradictions between the design, data contract, implementation steps, and smoke tests.
Retrieval check: A plan says "make job rows navigable using router.push." What are two review questions you should ask before accepting it?
Reveal answer

Ask: "Does this need to behave like a real link for keyboard users or open-in-new-tab?" and "Is the component already a Client Component, or does adding useRouter force a larger client boundary?"
