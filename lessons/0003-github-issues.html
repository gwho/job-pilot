Lesson 0003

GitHub Issues

How JobPilot uses GitHub Issues to track decisions, bugs, and work — and how to write one well.

One tangible win: after this lesson you will understand what a GitHub Issue is, why the format matters, and be able to read issue #19 in this project and explain every section of it.

What is a GitHub Issue?

A GitHub Issue is a recorded conversation about something that needs to happen to a codebase. It could be:

  • A bug — something is broken
  • A task — something needs to be built or changed
  • A question — something needs to be decided before work begins

An issue lives permanently on GitHub, attached to a specific repository. It is not a to-do list on your computer — it is shared with everyone who can see the project, including AI agents that run autonomously.

That last point matters for JobPilot. Some issues are written specifically so an AI coding agent can pick them up and implement them without a human in the loop. The issue is the spec.

The anatomy of a GitHub Issue

Every issue has these parts:

PartWhat it isExample from this project
Title A one-line summary of the work fix: fire job_found PostHog event for all saved jobs, not just strong matches
Body The full description — problem, decision, fix Explains what is broken, why it matters, and exactly what to change
Labels Tags that categorise the issue ready-for-agent
Assignee Who is responsible for it Can be a person, a team, or left blank for an agent to claim
Number A unique ID that never changes #19
State Open (not done) or Closed (done) Currently open — fix comes before Feature 17

Issue #19 — a real example

This issue was created during a Feature 11 session. Read the actual issue now: it is at github.com/gwho/job-pilot/issues/19. Or look at this condensed version:

title: fix: fire job_found PostHog event for all saved jobs,
       not just strong matches

## Problem

`job_found` is currently fired only for jobs with
`match_score >= 70` in `app/api/agent/find/route.ts`.

This causes a divergence in Feature 17 analytics:
- The "Total Jobs Found" stat card counts all jobs in the DB.
- The "Jobs Found Over Time" chart queries PostHog for
  `job_found` events — and therefore undercounts.

## Decision

`job_found` means "a job was discovered and saved",
not "a strong match was found".

## Fix (before Feature 17)

In `app/api/agent/find/route.ts`, move the `job_found`
event so it fires for every saved job, not just those
with match_score >= MATCH_THRESHOLD.

label: ready-for-agent

Notice how specific it is. It names the exact file (app/api/agent/find/route.ts), the exact problem (PostHog undercounting), the exact decision (fire for all jobs), and the exact fix (move the event call). A developer — or an AI agent — could implement this without asking any follow-up questions.

The label vocabulary in this project

Labels act as a status signal. Anyone reading the issue list can see at a glance what needs what:

LabelMeaning
needs-triageJust arrived — not yet categorised or prioritised
needs-infoBlocked — someone needs to answer a question before work can begin
ready-for-agentFully specified — an AI agent can pick this up and implement it without a human
ready-for-humanNeeds human judgment — a creative or architectural decision, not a mechanical fix
wontfixDeliberately not doing this — the issue stays closed for context but the work is skipped

What "the task is already done" means

Earlier in this session you asked: "should we create a GitHub issue for Vitest, or have you already finished the task?"

The answer: the task is done. Vitest is installed, configured, and running 25 passing tests. There is nothing left to track. GitHub issues are for work that has not happened yet. Once the work is merged, you close the issue — or in this case, you just never open one because you did the work immediately.

The only open issue right now is #19 — the PostHog event fix — because that fix belongs before Feature 17, not now. It needs to be tracked so it is not forgotten across sessions.

When to open an issue vs just doing the work

Open an issue

  • The work will happen in a future session or by a different person/agent
  • The decision needs to be recorded for context
  • You want to track a deferred bug before it is forgotten

Just do the work

  • You are implementing it right now in this session
  • The change is small and low-risk
  • No one else needs to approve or be aware of it

How to create an issue from the terminal

JobPilot uses the gh CLI (GitHub's official command-line tool). Issue #19 was created with:

gh issue create \
  --repo gwho/job-pilot \
  --title "fix: fire job_found PostHog event for all saved jobs, not just strong matches" \
  --body "## Problem
\`job_found\` is currently fired only for jobs with \`match_score >= 70\`..." \
  --label "ready-for-agent"

The --label flag only works if that label already exists in the repository. In this session we had to create the ready-for-agent label first with gh label create before we could apply it.

Retrieval check 1 — label selection

You discover that the "Generate Resume" button shows a spinner forever when the PDF fails to generate — it never resets to the normal button state. You cannot fix it right now. Which label do you apply?

Reveal answer

ready-for-agent if the fix is clear and mechanical (e.g. "add a finally block that resets isGenerating to false"). needs-info if you are not sure yet whether the problem is in the API route, the Server Action, or the client component. needs-triage if you just discovered it and have not investigated at all.

Retrieval check 2 — issue quality

Which issue title is better and why?

A: "bug in job search"
B: "fix: discovery search returns 0 results when location is empty string"
Reveal answer

B is far better. Title A gives no information — anyone reading the issue list cannot tell what is broken, where it is, or how to reproduce it. Title B specifies the symptom (0 results), the trigger (empty location string), and the context (discovery search). An agent reading B could start implementing a fix immediately. An agent reading A would have to investigate the entire codebase first.

Retrieval check 3 — open or close?

You finish implementing the issue #19 fix — moving the job_found event to fire for all saved jobs. What do you do with the issue?

Reveal answer

Close it. An issue represents work that needs to happen. Once the work is done and merged, the issue is resolved. You close it — not delete it — because the history of the decision is useful to keep. Anyone can look at the closed issue later and understand why the event was moved.

Practice: draft an issue

Without creating it on GitHub yet, write the title and body for this scenario:

"The jobs table doesn't show a loading state while a search is running. The user clicks Find Jobs and nothing visually changes for 10–20 seconds until jobs appear."

Write: a precise title, the problem, the affected file or component, and the fix. Then check: would a developer (or an AI agent) be able to implement it from your description alone?

Example answer 
title: enhancement: show loading skeleton in JobsTable while discovery search runs

## Problem

When the user clicks "Find Jobs", the jobs table shows no
feedback for 10–20 seconds while the Apify actor runs.
`isLoading` state exists in `FindJobsClient`, but `JobsTable`
does not receive it.

## Fix

Pass `isLoading` as a prop to `JobsTable`. While `isLoading`
is true, render 5 skeleton rows instead of the empty state
or actual jobs.

Affected files:
- `components/find-jobs/FindJobsClient.tsx` (pass prop)
- `components/find-jobs/JobsTable.tsx` (render skeleton)

label: ready-for-agent
