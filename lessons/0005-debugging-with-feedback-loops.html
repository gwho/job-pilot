Lesson 0005

Debugging with Feedback Loops

Grounded in the real debugging session from this project — FindJobsClient.tsx seam.test.tsx SearchControls.tsx

What you will understand by the end: what a silent failure is and why it's the hardest bug to notice; how to build a red-capable test that proves a bug exists; why a GREEN test is just as useful as a RED one; and how to apply the "minimal change" principle when fixing a bug.
Four parts — each builds on the last:
  1. Silent Failure — the bug category where nothing visibly breaks
  2. The Feedback Loop — building a test that can go RED on this exact bug
  3. The GREEN Test — how passing tests eliminate hypotheses
  4. The Fix — the minimal change that solved it

In Lesson 0002 you learned that a test is a question with a known answer, and that TDD means writing the test before the code. This lesson is about something different: using tests to hunt a bug that already exists in running code.

The bug came from a real user report on this project: "Whenever I click Find Jobs, the table only shows old results from before." The symptom pointed at old data. The actual cause was something completely different.

1
Silent Failure
Bug category

A silent failure is an error that happens but produces no observable change in the UI. The program doesn't crash. No red screen. No console message visible to the user. The page looks exactly the same as it did before.

This is what the handleSearch function in FindJobsClient.tsx was doing when the API returned an error:

if (!res.ok || !data.success) {
  console.error("[FindJobsClient] search failed:", data?.error);
  return;   // ← execution stops here
}

// These only run when search SUCCEEDS:
setJobs(data.jobs as Job[]);
setSearchStatus({ message: data.successMessage as string });
replaceViewState({ page: 1 });

When the Apify actor timed out (or the server returned any 5xx error), this branch ran. It called console.error — which writes to the browser's DevTools console, which most users never open — and then returned from the function. The three lines after it never ran.

From the user's perspective, the visible outcome was:

  1. Button showed "Finding jobs…" for 30–60 seconds
  2. Button re-enabled itself (the finally block ran — more on this in Part 4)
  3. Table still showed the same old jobs
  4. No banner appeared

Step 4 is what made this hard: the banner was the only thing that would have told the user "something went wrong." Without the banner, this was identical to a successful search that found no new jobs. The user couldn't tell the difference between the two.

Why console.error is not enough
A console.error writes a message to the browser's developer console. Developers see it because they have DevTools open. Real users never see it. If your error handling relies on console.error, it is invisible to users.
Retrieval check 1: A user clicks "Find Jobs." The button spins for 45 seconds, then becomes clickable again. No banner appears. The table is unchanged. Name two different causes that could produce this exact result.
Reveal answer
Two valid causes:
(A) The search SUCCEEDED but found no new jobs — the actor ran, all 10 discovered jobs were already saved in the database, so setJobs was called with the same existing jobs, and a success banner should have appeared but would say "all already saved."

(B) The search FAILED silently — the route returned an error, handleSearch hit the return branch, neither setJobs nor setSearchStatus was called, and the table and banner stayed exactly as they were.

The key point: the visible symptom was the same for both causes. Only the banner could tell them apart — and that was exactly what was broken.
2
The Feedback Loop
Diagnosing-bugs skill — Phase 1

The /diagnosing-bugs skill has one rule that overrides everything else: build a feedback loop before forming any hypothesis. A feedback loop is a test you can run in under two seconds that goes RED when the bug is present and GREEN when it is fixed.

Reading code to form a theory first is the failure mode. It anchors you on the first plausible idea — which is often wrong.

Before the fix, all 7 existing tests in seam.test.tsx used this helper:

function mockFetch(body: object) {
  global.fetch = vi.fn().mockResolvedValueOnce({
    ok: true,                            // ← always success
    json: () => Promise.resolve(body),
  });
}

Every test assumed the API worked. Zero tests simulated a failure. The error path had been in the codebase since the feature shipped — untested, silent, waiting.

Two new tests were written, each targeting a different possible cause:

// Test A — consecutive searches
// Question: does setJobs update correctly when you search twice?
global.fetch = vi.fn()
  .mockResolvedValueOnce({
    ok: true,
    json: () => Promise.resolve({ success: true, jobs: searchAJobs, ... }),
  })
  .mockResolvedValueOnce({
    ok: true,
    json: () => Promise.resolve({ success: true, jobs: searchBJobs, ... }),
  });
// Test B — error path
// Question: does an error show a banner, or just silently return?
global.fetch = vi.fn().mockResolvedValueOnce({
  ok: false,         // ← simulates a 500 error
  status: 500,
  json: () => Promise.resolve({
    success: false,
    error: "Job search failed. Please try again.",
  }),
});

Test B is the "red-capable" test: it drives the exact code path with the bug (if (!res.ok ...)), and it asserts the exact symptom the user described (an error message in the UI). When it ran against the buggy code, it timed out waiting for text that never appeared.

What "red-capable" means: a test that can go RED on this specific bug. Not "any test that fails" — a test whose failure message exactly matches what the user reported. After the fix, the same test goes GREEN. That GREEN is what proves the bug is gone.
Retrieval check 2: A test mocks a 500 API response and asserts expect(screen.queryByText(/error/i)).not.toBeInTheDocument(). Is this test red-capable for the silent failure bug? Explain why or why not.
Reveal answer
No — this is the wrong assertion.
not.toBeInTheDocument() asserts that the error text is absent. With the bug present, the error text IS absent (nothing shows), so this assertion passes — the test is GREEN when the bug exists. A red-capable test needs to assert that the error text IS present: expect(screen.getByText(/error/i)).toBeInTheDocument(). With the bug, this fails (RED). After the fix, it passes (GREEN).
3
The GREEN Test
Binary search on hypotheses

When Test A and Test B ran, only one failed:

Tests  1 failed | 7 passed (8)

✓  second search replaces first search results   ← Test A: GREEN
✗  shows error feedback when API returns failure ← Test B: RED

Test A going GREEN was not a wasted test run. It answered a question: does the component update correctly across multiple searches? The answer was yes. That eliminated three of the four live hypotheses in one command:

Hypothesis What it predicted Result
H2: setJobs breaks on second search Test A would be RED Eliminated (Test A GREEN)
H3: URL filters hide new results Test A would be RED Eliminated (Test A GREEN)
H4: job merging keeps old rows Test A would be RED Eliminated (Test A GREEN)
H1: error path silently returns Test B would be RED Confirmed (Test B RED)

This is binary search applied to hypotheses. A binary search doesn't check every possible value one by one — it picks the midpoint, reads the result, and eliminates half the search space. Here, Test A's GREEN result eliminated three-quarters of the hypothesis space at once.

If there had been four separate tests — one per hypothesis — and they ran one at a time starting from H2, it would have taken three failing runs to reach H1. Two carefully chosen tests reached H1 in one run.

Retrieval check 3: If Test A had gone RED instead of GREEN, what would that have meant — and would you still need to run Test B?
Reveal answer
RED Test A would have confirmed H2, H3, or H4 — the component state is not updating correctly across multiple searches. You would NOT need to run Test B next, because Test B is about the error path. The investigation would instead focus on why setJobs or the filtered memo isn't producing the right output on a second search.

The key insight: each test result narrows the next question. You follow the evidence, not a predetermined order.
4
The Fix
Minimal change principle

Once H1 was confirmed, the fix was straightforward: the error path needed to call setSearchStatus, just like the success path did. The test told us exactly what was missing.

Three options were considered. Here is why two were rejected:

Option B: add a separate errorMessage state
const [errorMessage, setErrorMessage] = useState<string | null>(null);

Creates a second banner. Now both searchStatus and errorMessage need to be cleared at the start of each search. If you forget to clear one, both banners show at once. More code, more edge cases, more things to get wrong.
Option C: throw an error for React's Error Boundary to catch
throw new Error(data?.error);

Error Boundaries are for crashes — unexpected errors that break the rendering tree. A 500 from the API is expected. It happens when the actor times out. Treating it like a crash would show the user a full-page error screen for something they should just be able to retry.
Option A: add isError: true to the existing searchStatus state (chosen)
The banner already existed. The searchStatus state already existed. The error path just wasn't using them. The minimal fix: call setSearchStatus with an error message. No new components, no new state, no new rendering path.

Here is the fix in FindJobsClient.tsx:

// SearchStatus type — one new optional field
type SearchStatus = {
  message: string;
  isError?: boolean;   // ← added
};

// Error path — now calls setSearchStatus
if (!res.ok || !data.success) {
  console.error("[FindJobsClient] search failed:", data?.error);
  setSearchStatus({                                       // ← added
    message: (data?.error as string) ?? "Search failed. Please try again.",
    isError: true,
  });
  return;
}

And in SearchControls.tsx — the banner now reads isError to switch between green and red:

{searchStatus && (
  <div
    className={`mt-4 flex items-center gap-2 text-sm rounded-md px-4 py-2 ${
      searchStatus.isError
        ? "bg-error/10 text-error"            // ← red banner
        : "bg-success-lightest text-success-foreground"  // ← green banner
    }`}
  >
    {searchStatus.isError ? <AlertCircle size={14} /> : <Sparkles size={14} />}
    {searchStatus.message}
  </div>
)}

Why isError? is optional (not required)

The ? makes isError optional. That means the existing success-path code didn't need to change:

setSearchStatus({ message: data.successMessage as string });
// isError is not passed → it's undefined → treated as falsy → green banner

If isError were required, every setSearchStatus call would need to pass it explicitly. Making it optional means "not passed" automatically means "not an error." Less code to change, smaller risk of breaking existing behaviour.

Why finally already handled loading state correctly

You may have noticed that setIsLoading(false) runs even on the error path. That's because it lives in a finally block:

async function handleSearch() {
  setIsLoading(true);
  try {
    // ... fetch, check errors, set jobs ...
    if (!res.ok) {
      setSearchStatus({ ... isError: true });
      return;          // ← jumps to finally
    }
  } catch (error) {
    // ...            ← also jumps to finally
  } finally {
    setIsLoading(false);  // ← ALWAYS runs, no matter what
  }
}

finally runs on every exit from the try block — including a return statement. This is the JavaScript equivalent of a software pattern called guaranteed cleanup: the loading state is always released, on every code path, with no exceptions.

A second new test confirmed this was already correct before the fix — the button was never stuck in loading state:

it("clears the loading state after an API error so the button is re-enabled", async () => {
  // mock: { ok: false }
  await clickFindJobs();
  await waitFor(() => {
    const btn = screen.getByRole("button", { name: /find jobs/i });
    expect(btn).not.toBeDisabled();    // ← passes on buggy AND fixed code
  });
});
Retrieval check 4: The catch block at the bottom of handleSearch still only calls console.error — it does not call setSearchStatus. When does the catch block run (vs the if (!res.ok) branch)? Is the catch path also a silent failure?
Reveal answer
The catch block runs when fetch itself throws — not when the server returns an error. fetch throws on network-level failures: no internet connection, DNS failure, the request being aborted. It does NOT throw for 4xx or 5xx HTTP responses — those resolve normally with ok: false, handled by the if branch.

Yes, the catch path is also a silent failure. If your WiFi drops mid-search, the user sees the same thing: spinner stops, old table, no banner. This was intentionally left unfixed in the same session — the fix would be identical (add setSearchStatus({ message: "Network error...", isError: true })), but it needs its own test first. One bug at a time, one test at a time.

The debugging process in one diagram

User report: "shows old results after search" │ ▼ ┌─────────────────────────────────────────────┐ │ Phase 1: Build a feedback loop │ │ DON'T form a hypothesis yet │ │ Write tests targeting the most plausible │ │ failure modes │ └─────────────────┬───────────────────────────┘ │ ▼ run tests Test A (consecutive searches): GREEN → H2/H3/H4 eliminated Test B (error path): RED → H1 confirmed │ ▼ ┌─────────────────────────────────────────────┐ │ Phase 2: Minimise │ │ The minimal repro: mock { ok: false } │ │ assert banner text → times out (bug proven)│ └─────────────────┬───────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────┐ │ Phase 5: Fix + regression test │ │ Add setSearchStatus to the error path │ │ Run Test B → now GREEN │ │ All 37 tests pass │ └─────────────────────────────────────────────┘
The three things you just learned:
1. Silent failures — errors that leave the UI unchanged, invisible to users unless you have a test that checks the error path.
2. Red-capable tests — tests that assert the user's exact symptom, not just "the component didn't crash."
3. GREEN tests eliminate hypotheses — a passing test in a debugging session is useful evidence, not wasted effort. Binary search on hypotheses.
