Lesson 0007

Feature 12 — Overview, Route Design, and the Server Data Flow

Goal: understand what Feature 12 adds to JobPilot, why its route lives where it does, and trace the exact server-side path from URL to rendered page. Series: Feature 12 Deep Dive (1 of 4).

One sentence version: Feature 12 adds a per-job detail page at /find-jobs/[id]. The page is a Server Component that authenticates the user, queries only their own job, and renders five display components — no agents, no mutations.

1 — What Feature 12 adds to the product

Feature 11 gave the Find Jobs table filter, sort, and pagination — but clicking a row did nothing. The table had cursor-pointer styling and no destination. Feature 12 is that destination.

Open context/project-overview.md. Under "Job Details Page" it specifies:

  • Full structured job information: title, company, location, salary, job type, date found
  • About the role (the full description)
  • Match score section: score, matched skills, missing skills, match reason
  • Company Research section: empty state + Research Company button (wired in Feature 13)
  • Apply Now button — opens external apply URL in new tab

All of this data already exists in the jobs table. Feature 12 adds zero new data — it reads and displays what Features 10 and 10b wrote. That is the correct sequencing: collect, then display.

Review question to ask: Does this plan depend on data that isn't in the DB yet? If yes, it should come after the feature that writes that data, not before.
Retrieval check: Where does the job description text (about_role) come from, and when was it written to the DB?
The Apify actor scrapes it from the JobsDB listing page and returns it as about_role. The find route (app/api/agent/find/route.ts) saves it to the jobs table during Feature 10b's job discovery flow — before Feature 12 ever existed. Feature 12 only reads it.

2 — Route design: why app/find-jobs/[id]/page.tsx

Open context/architecture.md. The folder structure section shows:

app/
  find-jobs/
    page.tsx          → /find-jobs (the table)
    [id]/
      page.tsx        → /find-jobs/[id] (the detail page)

The square-bracket folder [id] is Next.js App Router syntax for a dynamic segment. Any URL matching /find-jobs/something (where "something" is any string) renders this page. The string becomes a parameter called id.

Why this location and not somewhere else?

  • Nested under find-jobs/ — it is a sub-view of the Find Jobs feature. The Back to Jobs link goes to /find-jobs. The URL nesting mirrors the product hierarchy.
  • [id] is the DB row UUID — not a slug, not a sequential number. The UUID is already the job's primary key, so no extra lookup is needed.
  • Server Component by default — Next.js App Router makes every page.tsx a Server Component unless you add "use client". Feature 12 needs auth cookies and DB access — both are server concerns. It has zero interactive JavaScript needs. Server Component is correct.

Correct

app/find-jobs/[id]/page.tsx
// Server Component
// Auth + DB in page
// Props from DB to components

Wrong

app/find-jobs/[id]/page.tsx
"use client"
// fetches on client
// exposes user token to browser
Retrieval check: If the route were a Client Component that fetched the job via useEffect, what two things would break?
1. Auth cookie access — auth cookies are httpOnly (server-only). A client component cannot read them. You'd need a separate API endpoint just to get the user's session, adding a round trip.

2. Security — you'd have to send the job UUID in a client-side fetch, and you'd need to ensure the API validates user_id — an extra layer that the current approach handles inline in the Server Component, where auth is guaranteed before the DB call.

3 — force-dynamic: what it means and why it's required

Open app/find-jobs/[id]/page.tsx, line 14:

export const dynamic = "force-dynamic";

Next.js App Router tries to pre-render pages at build time when it can. A page that doesn't read dynamic data (cookies, headers, DB) might be rendered to static HTML during npm run build.

This page cannot be statically generated because:

  1. It reads auth cookies — no session exists at build time
  2. It queries per-user data — different content for every user
  3. Jobs are added after build — a job saved today would 404

force-dynamic tells Next.js: skip pre-rendering entirely, render on every request. Without it, Next.js may attempt static generation and fail during npm run build because createInsforgeServer() requires a real request context to read cookies.

Review question to ask: Does this page read cookies, headers, or per-user DB data? If yes — force-dynamic must be present. If the plan omits it on a page like this, flag it.

4 — The server data flow, step by step

Open app/find-jobs/[id]/page.tsx and read the full file. Here is the complete flow:

// Step 1 — resolve the dynamic segment
const { id } = await params;

// Step 2 — create a server-side DB/auth client
const insforge = await createInsforgeServer();

// Step 3 — authenticate the user
const { data: authData, error: authError } =
  await insforge.auth.getCurrentUser();
if (authError || !authData.user) redirect("/login");

// Step 4 — query only the current user's job by ID
const { data: job, error } = await insforge.database
  .from("jobs")
  .select("*")
  .eq("id", id)               // ← the URL segment
  .eq("user_id", authData.user.id)  // ← security boundary
  .single();

// Step 5 — 404 if job not found or belongs to another user
if (error || !job) notFound();

// Step 6 — assert the type (InsForge returns untyped data)
const typedJob = job as Job; // InsForge returns untyped query data

Each step has a specific failure mode and handling:

StepWhat can go wrongWhat happens
await paramsForgot to await (Next.js 16 trap)id is undefined, all queries return empty, notFound fires
getCurrentUserSession expired or missingredirect("/login")
DB queryWrong UUID / belongs to other usernotFound() — 404, not 403
DB queryNetwork errornotFound() (error is set)
Why notFound() for both "wrong user" and "wrong ID"? A 403 response tells the caller "this record exists but you can't see it." A 404 says "we have no information about this URL." For private per-user data, 404 is the security-correct response — it reveals nothing about whether other users' records exist.

The two-filter security pattern

.eq("id", id)
.eq("user_id", authData.user.id)

Job IDs are UUIDs — 128-bit values that cannot be guessed at random. But they are not secret. They appear in browser history, server logs, shared links, and analytics dashboards. Without the user_id filter, any authenticated user could view another user's job by knowing the UUID.

With both filters: if the job exists but belongs to a different user, InsForge returns { data: null, error: { code: 'PGRST116' } }. The code calls notFound(). The unauthorized user sees a 404.

Retrieval check: This project has Row-Level Security (RLS) on the jobs table. If RLS already prevents unauthorized reads, why is the user_id filter in the application still necessary?
Defence in depth. RLS is one layer — if it is misconfigured, disabled, or bypassed (via a service-role key in an admin route), the application-level filter still enforces ownership. Two independent enforcement points are more robust than one. The filter costs nothing and provides a safety net for any scenario where RLS is not in effect.

5 — Next.js 16: params is a Promise

Open app/find-jobs/[id]/page.tsx, lines 16–21:

export default async function JobDetailsPage({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const { id } = await params;

In every Next.js version before 16, params was a plain synchronous object. The pre-16 shape:

// PRE-16 — compiles in Next.js 16 but is WRONG
function Page({ params }: { params: { id: string } }) {
  const id = params.id; // ← undefined at runtime in Next.js 16
}

Next.js 16 changed params to be asynchronous. If you read params.id without awaiting, TypeScript does not warn you. You are reading the .id property on a Promise object. That property doesn't exist, so you get undefined.

What happens with id = undefined? The DB query becomes .eq("id", undefined), which returns no rows, which triggers notFound(). Every single job detail URL returns 404. The bug is completely silent — no TypeScript error, no build error, no test failure.

This is exactly why AGENTS.md says:

"Read node_modules/next/dist/docs/ before writing any code. Heed deprecation notices."

The installed version is the authority. Training data, blog posts, and AI-generated examples all show the pre-16 shape and are wrong for this repo.

Review question to ask: Does this plan show params: { id: string } (sync) or params: Promise<{ id: string }> (async)? If the plan was written from AI training data rather than the installed docs, it likely shows the sync shape. Flag it. The symptom is universal 404s with no error.
Retrieval check: Why doesn't TypeScript flag params.id when params is typed as Promise<{ id: string }>?
Because TypeScript only checks whether a property access is valid according to the type. Promise<{ id: string }> does not have an .id property in its definition, so accessing it returns undefined — but TypeScript does not error on reading an undefined property on an object type unless you enable strict null checks and the type explicitly excludes that key. In practice, TypeScript's inference allows property access on objects and returns the type of the declared properties — accessing a non-existent key yields undefined which is assignable to many types. The compiler does not see this as a type error.

Summary

  • Feature 12 displays data Features 10/10b already wrote — no new agent calls or DB mutations.
  • The route app/find-jobs/[id]/page.tsx is a Server Component — correct for auth, DB access, and zero client interactivity.
  • force-dynamic prevents Next.js from trying to pre-render a per-user auth-gated page.
  • The two-filter query (.eq("id", id).eq("user_id", ...)) is the security boundary — always scope to both ID and user.
  • Next.js 16 params is a Promise — must be awaited. TypeScript won't catch the mistake. Read the installed docs.
