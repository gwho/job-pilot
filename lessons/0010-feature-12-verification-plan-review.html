Lesson 0010

Feature 12 — Verification Mindset and Plan Review Exercise

Goal: understand what each verification step actually proves and doesn't prove, then practice reviewing a deliberately flawed plan using the Feature 12 checklist. Series: Feature 12 Deep Dive (4 of 4).

1 — What verification proves (and doesn't)

Feature 12's verification steps from the plan:

  1. npm run build
  2. npm run test:run
  3. Manual smoke test on a real saved job

Each step proves a different class of correctness. Knowing what each one cannot prove is as important as knowing what it can.

Step What it proves What it does NOT prove
npm run build TypeScript types are consistent. Next.js can compile the route and all imports resolve. No export errors. Data is correct at runtime. Auth flow works. Null states render correctly. The params await actually runs.
npm run test:run Utility functions (formatRelativeDate, getMatchBarColor) produce correct outputs. Existing functionality hasn't regressed. Server Components render. DB queries succeed. Any Feature 12 component actually works — there are no tests for Feature 12 components.
Manual smoke test The golden path works: click row → detail page loads → apply button opens URL → back button returns to list. Edge cases: null salary, null match_reason, missing skills arrays, invalid UUID in URL, unauthorised access by another user.

The plan explicitly specifies what to smoke test — not just "test it works" but specific cases:

  • Right-click → "Open in new tab" (stretched link native behaviour)
  • Apply Now goes to external_apply_url, not source_url (verify they differ)
  • Test a job missing salary and match_reason — confirm "—" and no AI card

The params await is a perfect example of something the build cannot catch. Forgetting to await params in Next.js 16 compiles cleanly. The type error is silent. The only proof that it works is running the app.

Review question to ask: Does the plan's verification section specify edge cases to test? "npm run build passes" is not a verification plan — it's a baseline. Ask: what happens when every nullable field is null? Ask: what does an unauthorised user see when they guess a valid UUID?
Retrieval check: npm run test:run passed with 42 tests before and after Feature 12. Does this tell you whether the JobInfo component renders the match badge correctly when match_score is 68?
No. The test suite has no tests for Feature 12 components. The 42 tests cover utilities (formatRelativeDate, getMatchBarColor, MATCH_THRESHOLD) and probably other pre-existing features. Whether matchBadgeClasses(68) returns the warning-range classes can only be verified by reading JobInfo.tsx directly or by running the component with a job whose score is 68. Test count passing means "nothing that was working before has broken" — it says nothing about new components.

2 — Plan review methodology: the C-E-C frame

When reviewing a coding-agent plan, use the Claim → Evidence → Consequence frame for every decision in the plan:

  1. Claim: What decision is the plan making?
  2. Evidence: What in the codebase or architecture docs supports or contradicts it?
  3. Consequence: What breaks if the plan is wrong?

Example applied to a Feature 12 decision:

FrameApplied to: "Use stretched link for row navigation"
Claim The plan uses a CSS pseudo-element stretched link instead of onClick + router.push
Evidence Architecture docs say Server Components only. JobsTable.tsx is already "use client" (it has sort state). Stretched link works in client components too. Stretched link gives native browser right-click and middle-click. The plan's own watchpoint 2 identifies the browser compatibility question.
Consequence If onClick were used: right-click "Open in new tab" would be absent. Screen readers couldn't navigate. The URL wouldn't be visible in the status bar on hover. Apply once — misses the standard.

3 — Plan review exercise

Below is a simplified, fictional alternative plan for a Feature 12-style job detail page. It has 5 deliberate errors. Read it carefully and identify all 5 before expanding the answer.

Take at least 2 minutes before revealing. Write down your answers.

Fictional Plan — "Job Detail Page v2"

Route: app/jobs/[id]/page.tsx — client component

"use client"
import { useParams, useRouter } from "next/navigation";
import { useEffect, useState } from "react";

export default function JobDetailPage() {
  const { id } = useParams(); // Next.js dynamic segment
  const [job, setJob] = useState(null);

  useEffect(() => {
    fetch(`/api/jobs/${id}`)
      .then(r => r.json())
      .then(setJob);
  }, [id]);

  if (!job) return <div>Loading...</div>;
  return <JobDetail job={job} />;
}

Component props:

function JobDetail({ job }) {
  return (
    <div className="bg-white rounded-2xl p-6 border border-gray-200">
      <h1 className="text-xl font-semibold text-gray-900">{job.title}</h1>
      <p className="text-gray-600">{job.company}</p>
      <p className="text-gray-600">{job.job_type ?? "Full-time"}</p>
      <p className="text-gray-600">{job.about_role}</p>
      <a href={job.external_apply_url}>Apply Now</a>
    </div>
  );
}

API route: app/api/jobs/[id]/route.ts — fetches by ID only

export async function GET(req, { params }) {
  const { id } = params; // Next.js 16
  const insforge = await createInsforgeServer();
  const { data: job } = await insforge.database
    .from("jobs")
    .select("*")
    .eq("id", id)
    .single();
  return Response.json(job);
}

Table row navigation:

<tr onClick={() => router.push(`/jobs/${id}`)}>
Reveal: the 5 errors and why each matters
  • Error 1 — Client Component with useEffect for data fetching. The plan uses "use client" and fetches via useEffect. This shows a loading spinner on every navigation (poor UX) and leaks the fetch path to the browser. Auth is handled by the API route — but now there's a whole extra roundtrip. A Server Component does this in one server-side call with no loading state. Consequence: performance regression, extra complexity, security concern if the API route doesn't validate user_id.
  • Error 2 — API route query has no user_id filter. The API route queries .eq("id", id) only. Any authenticated user can read any other user's job by guessing the UUID. The plan omits the security boundary. Consequence: broken authorisation — all user data is exposed to all authenticated users.
  • Error 3 — params in the API route is not awaited. The API route uses const { id } = params (sync pattern). In Next.js 16, params is a Promise — it must be await params. Without the await, id is undefined, the query returns nothing, and the client shows a loading spinner forever. Consequence: universal silent failure — no error, just an infinite loading state.
  • Error 4 — Raw Tailwind color classes and hex values. The JobDetail component uses bg-white, text-gray-900, text-gray-600, border-gray-200. These are raw Tailwind colors, not project tokens. The project rule is: only use token classes (bg-surface, text-text-primary, text-text-secondary, border-border). Consequence: design system drift — this component won't match the rest of the app and will look inconsistent, especially in dark mode or when tokens change.
  • Error 5 — job_type ?? "Full-time" invents a default. The plan renders job.job_type ?? "Full-time". Null means unknown, not full-time. Showing "Full-time" when the field is null misleads the user. The correct rule (from formatJobType): null → "—". Consequence: misinformation — a user might decline a part-time role or apply to a contract role expecting full-time hours, all because of a fabricated default.

Bonus catch: <a href={job.external_apply_url}> with no null check. If external_apply_url is null, the rendered href is "null" (the string). The plan should use externalApplyUrl ?? sourceUrl and handle the both-null case with a disabled button.

4 — Reusable review checklist for any job details-style feature

Print this page or open the cheat sheet for a condensed version.

Route and data flow

  • Is the page a Server Component? (no "use client")
  • Is force-dynamic set? (required for auth-gated, per-user pages)
  • Are params awaited? (Next.js 16: const { id } = await params)
  • Is the query scoped to both id AND user_id?
  • Does it notFound() for missing records (not 403)?
  • Does it redirect("/login") for unauthenticated access?

Design system

  • Are all colors project token classes? (no bg-white, text-gray-*, hex values)
  • Do card border radii follow the registry? (main: rounded-2xl, sub: rounded-xl)
  • Are buttons using token classes (bg-accent text-accent-foreground)?

Null and empty states

  • Is job_type: null shown as "—" (not "Full-time")?
  • Is salary: null shown as "—"?
  • Is match_score: null badge hidden entirely?
  • Is match_reason: null card hidden entirely?
  • Are empty skill arrays handled with a message?
  • Does Apply Now fall back to source_url when external_apply_url is null?
  • Is Apply Now disabled (not broken) when both URLs are null?
  • Does about_role: null show a message (not render empty)?
  • Does scraped text use whitespace-pre-line?

Navigation

  • Does row navigation use a stretched <Link> (not onClick)?
  • Does the <tr> have relative?
  • Does the <Link> have after:absolute after:inset-0 after:content-[''] after:z-1?
  • Does the stretched link have an aria-label?
  • Do external links have target="_blank" rel="noopener noreferrer"?

Component architecture

  • Are components in the path defined by architecture.md?
  • Are Server Components used (no unnecessary "use client")?
  • Is scope respected — no unplanned agents, mutations, or events?
  • Does the plan account for future change boundaries (e.g., which component will change next)?

Verification

  • Does the plan specify npm run build and npm run test:run?
  • Does the smoke test include null-field cases (not just golden path)?
  • Does it verify right-click "Open in new tab" on the stretched link?
  • Does it verify Apply Now goes to external_apply_url, not source_url?

Summary

  • Build proves type safety. Tests prove utility functions and non-regression. Smoke tests prove golden path. None of them prove edge cases.
  • Use C-E-C (Claim → Evidence → Consequence) to evaluate each plan decision: what did the plan decide, what evidence supports or contradicts it, what breaks if it's wrong?
  • The 5 errors in the fake plan map to 5 recurring failure modes: client-side data fetching, missing user_id filter, missing params await, raw Tailwind colors, null treated as a default value.
  • The review checklist covers every major decision area in Feature 12. Reuse it for any page-level feature that follows the same Server Component + per-user data + external links pattern.
