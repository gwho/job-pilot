Lesson 0002

TDD for Beginners

Using the real tests in __tests__/find-jobs/utils.test.ts as your guide.

One tangible win: after this lesson you will be able to read any test in this codebase and understand exactly what it is checking and why.

What is a test, in plain English?

A test is a question with a known answer. You ask the question by calling a function, and you check the answer using a special word called expect.

That is the whole idea. Everything else is just details.

The anatomy of one test

Open utils.test.ts. Look at lines 21–23:

it("returns 'all' for null", () => {
  expect(parseMatch(null)).toBe("all");
});

There are three parts. Read them right to left — it helps:

PartWhat it doesPlain English
it("returns 'all' for null", ...) Names the test "The thing I am checking is: it returns 'all' for null"
parseMatch(null) Calls the function "Ask the function: what do you give back when I pass null?"
expect(...).toBe("all") Checks the answer "I expect the answer to be exactly the string 'all'"

If the function gives back "all", the test passes. If it gives back anything else — "high", "", undefined — the test fails and Vitest prints a clear error message telling you exactly what went wrong.

What is describe?

It is just a label. It groups related tests together so the output is easier to read. Look at lines 14–30:

describe("parseMatch", () => {         // ← group label
  it("returns valid match values unchanged", () => { ... });
  it("returns 'all' for null", () => { ... });
  it("returns 'all' for invalid strings", () => { ... });
});

Three tests about parseMatch live inside one describe("parseMatch", ...) block. When you run npm run test:run, the output groups them under that label so you can find failures quickly.

What is TDD?

TDD stands for Test-Driven Development. It has one rule: write the test before you write the code.

The reason is not what most people think. The reason is not "to catch bugs." The reason is to force you to decide, precisely, what a function should do — before you start worrying about how to make it work.

The cycle has three steps:

  1. Red — Write a failing test.

    Write a test for the function you are about to build. Run it. It fails because the function does not exist yet. That red failure is expected and correct.

  2. Green — Write the minimum code to make it pass.

    Write just enough code to make that one test pass. Not more. Do not add features the test does not ask for.

  3. Refactor — Clean up.

    If the code is messy, clean it up now. The test is your safety net — if you break something while cleaning, the test turns red again immediately.

Then repeat. One test at a time.

A real TDD example from Feature 11

Here is exactly how parseMatch would have been built using TDD. Open lib/find-jobs-utils.ts alongside this so you can see the finished version.

Step 1 — Write a failing test

Before writing any code for parseMatch, the test file would already exist with this:

it("returns 'all' for null", () => {
  expect(parseMatch(null)).toBe("all");
});

Running npm run test:run would print: parseMatch is not a function. Red

Step 2 — Write the minimum code to pass

export function parseMatch(raw: string | null): MatchFilter {
  return "all";
}

This passes the null test. Green

But now the test "returns valid match values unchanged" fails because parseMatch("high") returns "all" instead of "high". Good. That failure tells you exactly what to add next.

Step 3 — Make all tests pass

export function parseMatch(raw: string | null): MatchFilter {
  return (["all", "high", "low"] as const).includes(raw as MatchFilter)
    ? (raw as MatchFilter)
    : "all";
}

All three tests pass. Green

Why tests were especially important for mergeJobsById

Look at lines 144–189 of the test file. The mergeJobsById function is the most important function in Feature 11 — it prevents data loss when two searches run. The test at line 154 checks the exact failure mode that existed before Feature 11:

it("overwrites existing jobs with incoming data on id collision", () => {
  const current = [{ id: "a", title: "Old A" }];
  const incoming = [{ id: "a", title: "New A" }];
  const result = mergeJobsById(current, incoming);
  expect(result).toHaveLength(1);      // only one job — deduplication worked
  expect(result[0].title).toBe("New A"); // newer data wins
});

Before this function was extracted, the old code did setJobs(data.jobs) — it replaced all existing jobs with only the latest search results. Running this test against the old code would have produced a red failure. The test would have caught the bug immediately.

Retrieval check 1 — read a test

Look at this test from lines 56–59 of utils.test.ts. Without running it, what must parsePage("1") return for this test to pass?

it("parses valid positive integers", () => {
  expect(parsePage("1")).toBe(1);
});
Reveal answer

The number 1 (an integer, not the string "1"). The test uses .toBe(1) which checks value and type. If parsePage returned the string "1" instead of the number 1, the test would fail.

Retrieval check 2 — name the TDD steps

You are about to add a parseProvider function that accepts "jobsdb", "adzuna", or null and defaults to "all". What are the three TDD steps in order?

Reveal answer
  1. Red — Write tests for parseProvider (for null, for valid values, for invalid strings). Run them. They fail because the function does not exist.
  2. Green — Write parseProvider in lib/find-jobs-utils.ts. Run the tests. They pass.
  3. Refactor — Notice that parseProvider looks almost identical to parseMatch. Could you extract a generic parseEnum helper? Clean it up now while the tests protect you.

Retrieval check 3 — predict a failure

Someone changes mergeJobsById to use the old approach: instead of a Map, it just does return [...current, ...incoming]. Which specific test in utils.test.ts turns red first?

Reveal answer

The test "overwrites existing jobs with incoming data on id collision" (line 154). That test checks result.toHaveLength(1) — but the broken version would return length 2 (both "Old A" and "New A" in the array, without deduplication). The red failure is precise: the test tells you exactly what contract was broken.
